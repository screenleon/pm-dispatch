# Test runner contract

pm-dispatch has two deliberately different test entry points. They solve
different problems and neither silently substitutes for the other.

For the full assurance picture, including dimensions beyond test coverage, see [the delivery assurance map](delivery-assurance-map.md).

## Iteration runner

`tests/bin/run-tests.sh` plans direct-impact suites from changed paths and invokes
the shared suite executor with explicit `--suite` selections. It is optimized for a
short edit/fix feedback loop.

```bash
bash tests/bin/run-tests.sh --base origin/main
bash tests/bin/run-tests.sh --path runtime/lib/pmctl-context.sh
bash tests/bin/run-tests.sh --base origin/main --list
```

The planner currently knows direct path-to-suite relationships only. It does
not claim a trustworthy transitive dependency graph. Every run therefore prints
`contract=iteration-only`; paths without a direct behavioral mapping are listed
as coverage gaps. Changes to high-fanout runner/install substrates escalate to
the full suite instead of returning an unsafe targeted result.

For an iterative reviewer gate, the caller may opt in explicitly through the
generic gate interface:

```bash
pmctl gate run \
  --cd /path/to/pm-dispatch \
  --test-cmd 'bash tests/bin/run-tests.sh --base origin/main' \
  --lifecycle detached
```

`pr-gate` does not auto-detect this command or any runner filename. Other repos
remain free to supply their own `--test-cmd`, or none.

`--test-cmd` runs in the working tree, so it cannot be combined with `--head <ref>`: the gate
refuses that pair before dispatching anything. Check the ref out and run without `--head`,
or pass `--skip-preflight-tests`.

Every explicit pre-flight command receives a portable basic evidence envelope:
hashed command identity, status/exit code, timing/timeout, and a digested log.
The command itself does not need to implement a pm-dispatch protocol. Generic
commands such as `npm run test` produce opaque/advisory coverage: QA may cite
the aggregate PASS, but may still run the minimum repo-native validation needed
when behavioral coverage cannot be established.

`tests/bin/run-tests.sh` additionally detects the gate-provided result sink and
emits structured coverage automatically. Its `pm_test_result_v2` records the
planner-derived inputs, selection mode, registry-ordered suites, each suite's
pass/fail/timeout/skip status and duration, and aggregate counts. Current PASS
suites in this structured form use the no-duplicate reuse policy. Planner
inputs such as changed paths are generated by the runner; users do not supply
evidence fields manually.

The injected per-suite result sink is mandatory for recorded evidence. An
empty, malformed, or missing sink fails closed; the wrapper never fabricates
per-suite PASS records from a process exit code, and such a run cannot become
authoritative evidence.

### Changes to high-fanout files, and slow hosts

A change to a file that every suite depends on (`tests/lib/test-harness.sh`, the runner and
install substrate) makes `tests/bin/run-tests.sh` escalate to the full suite, because a narrower
selection would be unsafe. That takes a long time, longer still on native Windows.
The qa-tester's supplemental commands run through a helper with a short `--timeout` that the
reviewer chooses, so a supplemental run that escalates is cut off. The host records that as
`attempt.status: timeout` in `qa-execution-*.json` and the reviewer is told that a timeout
cannot support a GO by itself: it is a gap to report, and a blocking finding if the log shows a
stall in code the diff touches. The host enforces this too: unless a pre-flight run passed, a
`Final: GO` is refused before anything is published when the qa-tester's evidence is
`inconclusive` (a timeout, a nonzero exit, or an attempt that never finished) or cannot be read
(missing, a symlink, not JSON); `pr-gate.sh` exits 1 and the result is kept as a `failure-result:`
for inspection, with its `Final` lines rewritten to INCOMPLETE. Only the last supplemental command
is judged (end with the passing suite), except that a timeout stays on the record. Any passing
`--test-cmd` lifts the refusal, whether or not it covers the diff, and `--head` cannot be combined
with `--test-cmd`. The pre-flight command has its own, much larger budget
(`--test-timeout`, default 3600 s) and is independent of any reviewer, so for such a change put
the whole run there (and detach, since it takes long):

```bash
pmctl gate run --cd /path/to/pm-dispatch --lifecycle detached \
  --test-cmd 'bash tests/bin/run-tests.sh --base origin/main' --test-timeout 7200
```

`run-tests.sh` then runs the whole registry (it records the run as `escalated-full`). The brief
tells the qa-tester how the budget works, and the escalation message of `run-tests.sh` states
how many suites it is about to run.

### Budget handshake for supplemental QA commands

The brief is advice, and a reviewer can ignore it: it can still run an announced full suite with a
`--timeout` of a few minutes, and the cut-off leaves a timeout on the QA evidence for the rest of the
gate. So the helper also passes the budget to the command itself. It exports
`PM_QA_ATTEMPT_TIMEOUT_SECS`, the `--timeout` of this one attempt in seconds, into the environment of
the command it runs.

A repo runner may honour it. The contract for a runner that does:

- **Refuse work that cannot fit, before doing it.** A full suite is never a supplemental QA command.
  `tests/bin/run-tests.sh` refuses both an escalation to the full suite and `--all` while the variable
  is set: it prints why, names the pre-flight as the place for the full run, and exits **3** without
  starting anything. Listing (`--list`) and targeted selections are unaffected.
- **Refuse with an ordinary nonzero exit, never 124 or 137.** The helper records a refusal as a nonzero
  attempt: the evidence reads `inconclusive` until a later attempt passes, and then `completed`. A
  timeout, by contrast, stays on the evidence (`attempt_timeouts`) whatever runs afterwards.
- **Do nothing when the variable is unset or empty.** The gate pre-flight (`--test-cmd`), a developer,
  and CI do not run inside an attempt, and the same escalation there runs as before.

A repo whose runner does not know the variable behaves as before; the brief guidance (CC-617) is all it has.

What this does not do: it does not make a high-fanout change verifiable inside the QA stage. The reviewer
now gets an immediate, explicit refusal instead of a timeout, and reports the gap, and the evidence can
still end `completed` through a targeted suite. Full coverage for such a change comes from the pre-flight
above. Having the gate itself put the full run into the pre-flight when it sees a high-fanout change was
weighed and not done: the gate cannot know an arbitrary repo's test command (`--test-cmd` is the declared
interface), it would add a run of 40 minutes or more on a slow host to every such gate, and it changes who
pays that cost without the person asking for the gate choosing it.

## pm-dispatch development and PR policy

`tests/bin/run-all-tests.sh` is the backward-compatible full-suite entry point; it
delegates to `tests/bin/run-tests.sh --all`. For this repository's own delivery
workflow, run it independently of the PR-gate lifecycle so its wall-clock
budget cannot consume the gate supervisor/reviewer budget:

```bash
bash tests/bin/run-all-tests.sh
```

The full runner remains parallel by default. It uses the detected CPU count
up to four concurrent suites; set `PM_DISPATCH_TEST_MAX_JOBS` or pass
`--jobs` when a measured environment can safely support a different limit.

The pm-dispatch maintainer's development and PR policy is deliberately
asymmetric:

1. During implementation and an optional PR-gate review, run affected suites
   for fast feedback.
2. Immediately before creating a pm-dispatch PR, run
   `tests/bin/run-all-tests.sh` outside the gate lifecycle. It writes
   `.pm-dispatch/test-results/latest-full.json` (`pm_test_result_v2`).
3. Verify that artifact against the still-current source tree before opening
   the pm-dispatch PR:

       bash tests/bin/run-tests.sh --verify-full .pm-dispatch/test-results/latest-full.json

The verifier accepts only an authoritative full PASS with no requested or
suite-level skips, the complete current suite registry, an unchanged tree
during the run, and matching current tree + runner-contract fingerprints.
Individual cases may use `skip_platform` for a documented host-platform
exclusion (for example Windows ACL checks on Linux). They remain SKIP in logs
and `case_skips` counts, with the accepted subset in `platform_case_skips`
and aggregate `platform_case_skipped`; they are never counted as passed cases.
Review the recorded reasons and run the native-platform checks separately when
changing that platform's behavior. Missing dependencies on an applicable host
and unclassified `skip` calls still prevent full sign-off. Fractional counts,
platform counts exceeding total skips, and inconsistent aggregate counts are
rejected. Any edit after the full run invalidates the evidence and requires
another full run.

These three steps end at PR creation. They are not a release workflow and
affected-suite feedback is not a fixed release phase.

## Fixed pm-dispatch release procedure

The single automated release entry point is:

```bash
bash ops/release/release-verify.sh --e2e
```

`release-verify.sh --e2e` always performs a fresh `run-all-tests.sh` in Phase 2,
verifies its new tree-bound artifact, runs the real-binary smoke phases, and
adds the live dispatch + pr-gate Phase 4. A separate affected-suite run or a
second standalone `run-all-tests.sh` is not a fixed release prerequisite.
`--no-suite` remains an explicit diagnostic escape hatch and can produce only
PARTIAL GO, never a pm-dispatch release sign-off. The remaining environment-
mutating checks are fixed by `docs/RELEASE_CHECKLIST.md` and must be completed
before tagging.

Both the development/PR policy and the release procedure are pm-dispatch
maintainer choices, not requirements imposed by the generic tools. Each
capability remains independently callable: another repository may use
`--test-cmd` with its own runner, use a gate with no test command, run tests
without a gate, or use neither. `pr-gate` does not select or enforce a workflow
profile, and pm-dispatch does not ship a generic profile engine.

## Aggregator selection primitive

The internal suite executor's `--suite <name>` is repeatable and runs only the
named, registered suites in registry order. Unknown names fail before execution.
`run-tests.sh` owns that primitive; `run-all-tests.sh` deliberately exposes only
the same runner's `--all` compatibility mode.
