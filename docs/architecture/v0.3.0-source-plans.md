# pm-dispatch v0.3.0 — Source Planning Inputs

This file preserves the three independent architecture plans that fed
[`v0.3.0-synthesis.md`](v0.3.0-synthesis.md). They were produced from a shared
brief and are kept verbatim (ChatGPT condensed — see §1) so the synthesis is
auditable and so disagreements between models remain inspectable.

A fourth input from an **AGY CLI** was planned but AGY is not yet integrated into
the toolchain; §4 is a placeholder.

---

## 1. ChatGPT (user-supplied seed plan — condensed)

The ChatGPT plan was provided by the maintainer as the starting point. Full text
lives in the originating session; its substantive proposals:

- Restructure pm-dispatch into `core/` (domain model + policies + prompts),
  `runtime/` (`pmctl` + libs: store, executor-router, handover, guard-engine,
  event-log, memory-extract, report, worktree), `adapters/` (claude/codex/gemini/
  opencode), `mcp/`, plus `agents/`, `skills/`, `docs/`.
- Add a **state substrate**: `~/.pm-dispatch/pm.sqlite3` for metadata/index +
  files for long content (briefs, traces, gate results, reports).
- Map the four external projects: Multica → task/run lifecycle; Memori →
  execution memory + memory candidates; Superpowers → skill-trigger engine
  (`core/policies/skill-triggers.yml`); AI Night Shift → ops loop (heartbeat /
  patrol / morning-report).
- MCP in three phases: read-only resources → safe mutation tools → execution
  tools, each gated through `pmctl`.
- Spike agent as planner/synthesizer (runtime does the fan-out); reuse/refactor
  as a capability pipeline (reuse-scan → reuse-judge → refactor-plan →
  refactor-execute → refactor-gate).
- A follow-up message reframed `CC-209` (codegraph) as a **context-enrichment
  spike** and introduced a **context-pack** abstraction: a `context-pack.json`
  assembled before dispatch from pluggable sources (codegraph / rg / git /
  memory), consumed by `pmctl context build` rather than a Codex-specific flag.

**Known defects** (corrected in the synthesis): proposed ticket IDs
`CC-222`/`CC-224`/`CC-225`/`CC-226` collide with already-assigned tickets; the
scope (core + runtime + four adapters + MCP + context-enricher in one version) is
a rewrite-sized over-reach.

The two genuinely distinctive contributions kept by the synthesis: the
**context-pack / context-enricher abstraction**, and the explicit phased MCP
consent model.

## 2. Codex (independent plan — verbatim)

> Produced via `codex-dispatch.sh` from the shared brief; trace
> `codex-20260522-231239`.

### 1) Target architecture (layered shape, strict responsibilities)

- `core/` = canonical domain model and state transitions.
- `runtime/` = `pmctl` CLI orchestration, policy/guard engine, trace & event
  pipeline, validation facade.
- `adapters/` = concrete executor/front-end bridges only (Claude, Codex, future
  Gemini/OpenCode).
- `mcp/` = external MCP tool surface built on `runtime/` APIs.

`core/` owns task/run/event schemas, lifecycle and state transitions, the blocker
model, handoff schema. `core/` must not know shell syntax, CLI specifics, memory
card formats, or UI wording. `runtime/` owns `pmctl` command parsing and execution
graph, adapter dispatch policy, event capture / locking / idempotency / trace
correlation, protocol-level guard checks. `adapters/` translate normalized run
specs into CLI invocations and normalize output; they own no lifecycle/state or
gate-decision logic. `mcp/` owns tool contracts and auth/quota/session context;
all decisions go through `runtime/`.

### 2) State / schema substrate

First-class objects: `Project`, `Task` (type delivery|spike|reuse|refactor),
`TaskRun`, `LifeCycleEvent`, `Blocker`, `Memory` (Memori-inspired layers:
EntityFact / Process / Session / Rule / Skill), `ReviewPacket`, `Artifact`.

On-disk under `~/.claude/projects/<project-id>/pmctl/`: `state/project.json`,
`state/tasks/{id}.json`, `state/runs/{id}.json`, `state/events.ndjson`,
`state/blockers/`, `state/memory/events.ndjson`,
`state/memory/derived/{entities,processes,rules,skills}.ndjson`,
`state/trace/{run-id}/`, `views/` (generated Markdown projections), `index/`.

Markdown-vs-structured: structured JSON/JSONL is source of truth; Markdown remains
the injection index (`MEMORY.md`), durable cards, and release notes. A projection
step (`pmctl memory sync`) rebuilds Markdown cards from `state/memory/*`.
`episodes.jsonl` stays append-only; `pmctl` enriches it into
`state/memory/events.ndjson`.

### 3) External-concept mapping

- **Multica** → queue lifecycle (claim/start/progress/blocked/complete/fail) as
  the native `Task` state machine; agent pool → executor adapter pool.
- **Memori** → tool findings, review outputs, execution traces become
  `state/memory/events`; periodic compaction maps facts into layers; rule/
  preference updates become generated Markdown card updates with evidence IDs.
- **Superpowers** → mandatory pre-implementation quality stage as state
  preconditions; ≥3 behavioral units requires `qa_checklist` + scope check before
  `Task.state=planned`; auto-trigger skills become a runtime rules engine.
- **AI Night Shift** → `pmctl nightshift loop` with rounds/heartbeat/patrol;
  periodic `morning-report`; deterministic state-driven scheduling, not
  autonomous long-running agents.

### 4) MCP integration (phased)

Phase A — finalize core/runtime contracts, expose internal CLI subcommands with
dry-run, no MCP yet. Phase B — MCP read-only tools (`pm_list_tasks`,
`pm_get_task`, `pm_list_runs`, `pm_get_trace`, `pm_get_events`). Phase C — MCP
write tools with idempotency keys + dry-run preview, shared validator. Phase D —
adapter-native MCP session generator, write tools behind `PMCTL_MCP_BETA=1`.

### 5) Spike + reuse/refactor

Spike: new `spike` task kind with investigation angles / evidence criteria /
decision gate / result pointer; runtime generates `docs/spikes/<id>.md` and tracks
progress as tasks/runs. Reuse/refactor: new `refactor`/`reuse` task kinds
consuming duplication candidates; output is migration note + duplication list +
decision; memory via the same pipeline. Reuse-debt closure: Phase 1 unify
validation/handover helpers, Phase 2 extract runner/policy libs, Phase 3 delete
duplicated scripts after regression is green.

### 6) Milestone breakdown (8 milestones)

1. Core foundation: schema + state event model (no dependency).
2. Runtime core extraction (`pmctl`) — depends on 1.
3. Contract migration: `/pm` and `/pr-gate` to `pmctl` — depends on 2.
4. Lifecycle + quality gates integration — depends on 3.
5. Memory v2 + Memori-layer projection — depends on 2 (+4 for evidence capture).
6. Spike + reuse/refactor module — depends on 1–5.
7. MCP bridge — depends on 3 (4 preferred).
8. Hardening + compatibility (trace migration, docs refresh, regression matrix,
   rollback) — depends on all.

### 7) Usability / DX

Single `pmctl` UX (`task queue --watch`, `task claim --next`, `task status
--project`, `run tail`, `run verify`, `gate run --targeted`); auto-generated
`views/summary.md`; concise failure summaries; resume-by-run-id; unchanged `/pm`
and `/pr-gate` command-level behavior.

### 8) Risks & what not to do first

Hard risks: state migration split-brain (mitigate with dual-write + read-through
window); hook-policy drift (single policy source); executor behavior mismatch
(adapter capability matrix + golden tests); event volume / lock contention
(compacted snapshots + append-locking + retention); Windows path/quoting edge
cases. What not to do first: MCP write APIs before runtime/lifecycle stable;
rewriting all hooks/adapters up front; replacing Markdown memory immediately;
introducing a new technology stack before core+runtime are stable.

## 3. Claude Opus 4.7 (independent plan — verbatim)

> Produced via a `Plan` subagent (model: opus) from the shared brief.

### 0. Reading of where the repo is today

pm-dispatch is a Markdown-and-Bash config bundle, not a runtime. Logic lives in
three drifting places: agent prompt files, slash-command prose-with-embedded-bash
(`commands/pm.md` carries ~10 runtime steps as English+code; `commands/pr-gate.md`
embeds a 50-line bash arg-parser), and tested shell. There is no state model —
tasks are `BACKLOG.md` rows, runs are `.agent-trace/*.jsonl` + a `routing_log.md`
auto-block, reviews are `.gate-results/` files, memory is Markdown cards +
`episodes.jsonl`; nothing connects ticket → dispatch → gate → decision. The tested
surface (`handover-validate.sh` 353 lines, `portable.sh` 871, `pr-gate.sh` 830,
`codex-dispatch.sh` 260, 30+ `test-*.sh`) is the asset to protect.

The single most important opinion: **CC-211's stated P0–P5 order is wrong** —
building `core/schemas/` + `pmctl` + four adapters + an MCP server in one version
is a rewrite disguised as a refactor. v0.3.0 should ship a state substrate and one
runtime spine, prove it against the existing Codex+Claude paths, and explicitly
defer multi-CLI adapters and MCP.

### 1. Target architecture

Four layers; the boundary that matters is layer 1 (data) vs everything else. Each
layer depends only on layers below. `core/` = definitions, zero behavior
(`core/schema/`, `core/policy/`); must not know hooks, `~/.claude`, or bash.
`runtime/` = the `pmctl` spine, the only layer that mutates state (state store,
dispatch runner, guard engine, validator, trace logger, report synthesizer); bash,
not Node/Python. `adapters/` = thin delivery shells, zero business logic (today's
`agents/`/`commands/`/`hook-*.sh` become `pmctl` callers). `adapters/codex/`,
`adapters/gemini/`, `mcp/` are named slots, not v0.3.0 deliverables. The split is
a dependency-direction discipline enforced by one cheap test, not a microservice
boundary — collapse a layer if it costs more than it saves.

### 2. State / schema substrate

Five entities: **Task** (`open→claimed→in-progress→blocked→done/dropped`), **Run**
(`pending→dispatched→verifying→ok/partial/failed`), **Event** (append-only),
**Review** (`pending→GO/NO-GO`), **Decision** (append-only).

Markdown-vs-structured — a hybrid with a clear rule: `BACKLOG.md`/`DECISIONS.md`
stay Markdown-primary (human-authored, daily-read; `pmctl` parses them, the
pm-schema grammar is the contract). Runs and Events become JSONL (machine-written
— `routing_log.md`'s machine-written Markdown table is the anti-pattern to kill).
Reviews become structured-with-rendered-Markdown. **The rule: human-authored →
Markdown, machine-authored → JSONL, never a machine-written Markdown table.**

On-disk: `core/schema/*.schema.json` in-repo; runtime state at
`~/.claude/.pm/state/` (per-machine, gitignored — "definitions in repo, state on
disk"); memory cards unchanged. The state store is JSONL append + a small index
with `serialize_with_lock()` (CC-104p); `pmctl` is the only writer.

### 3. External-concept mapping (each lands in a different layer of one substrate)

- **Multica** → *is* the Task/Run state machine in `core/policy/dispatch-states.md`
  — not a feature to add. Blockers become a Task state + Event type. Progress
  streaming reuses `codex-watch.sh`. Reject: parallel autonomous claiming.
- **Memori** → memory derived from the action stream — the Event log. `events.jsonl`
  is the deliverable; `core/schema/event.schema.json` is the Memori contribution.
  The existing four-tier card system already maps to Memori's layers. Reject:
  Memori as a separate engine.
- **Superpowers** → makes the spec→design→plan discipline (already advisory in
  `pre-impl.md`/`project-pm.md`) a Task lifecycle gate enforced by `pmctl`; seeds
  the empty `skills/` dir with 2–3 skills. Reject: a full auto-trigger framework.
- **AI Night Shift** → the most dangerous to absorb (autonomy conflicts with
  no-nested-subagents + maintainer-in-the-loop). Take only: append-only comms +
  time-boxed rounds (already present), and one read-only `pmctl report`
  morning-report. Reject for v0.3.0 and probably forever: the autonomy loop.

### 4. MCP — a v0.4.0 deliverable, named-but-not-built in v0.3.0

`CC-216` correctly depends on a stable `pmctl`. v0.3.0 creates `mcp/README.md`
defining the intended tool surface; this forces `pmctl`'s CLI to be designed as if
an MCP server will wrap it (every subcommand → one MCP tool, `--json` output). The
server itself is a thin `pmctl`-subprocess wrapper built in v0.4.0.

### 5. Spike + reuse/refactor under no-nested-subagents

`CC-218` (spike infrastructure) is cheap and lands early. `CC-220`'s "spike agent
dispatches parallel sub-agents" **will not run** — subagents cannot spawn
subagents. The fix is the existing `project-pm` pattern: `agents/spike.md` is a
*planner* that returns a `spike_plan` block; the **main thread** fans out one
`Agent` call per angle (as `/pr-gate` fans out reviewers); the spike agent is
re-invoked to synthesize. `commands/spike.md` is the main-thread orchestration
script.

Reuse/refactor (`CC-200..204`) is **not a separate capability — it is the
mechanism by which the layered architecture gets built**: CC-202 (handover
validator) → `pmctl validate`; CC-204 (hook framework) → the guard engine; CC-200
(executor-router) → the dispatch runner; CC-201 → a small lib helper; CC-203 →
`test-harness.sh`. The refactor *is* the architecture — grow `runtime/` by
extraction from tested code, not greenfield. No separate reuse/refactor agent is
needed.

### 6. Milestone breakdown (M0–M5)

- **M0** — cheap extractions, zero architecture risk: CC-201, CC-203, CC-218,
  CC-219, CC-217, CC-060.
- **M1** — the state/schema substrate: `core/schema/*`, re-home `pm/schema.md`,
  `core/policy/`, the `~/.claude/.pm/state/` store; ships no behavior change.
- **M2** — grow the runtime by extraction: CC-202, CC-204, CC-200, stand up
  `bin/pmctl` (CC-215) with `--json`; riskiest milestone (guard hooks).
- **M3** — re-point the Claude adapter: CC-059 (thin `pm.md`), shrink hooks/
  commands, `test-layer-boundaries.sh`, formalize `adapters/claude/`.
- **M4** — concept absorption: wire Multica lifecycle, Memori event-derived
  memory, Superpowers lifecycle gate, `pmctl report`, seed `skills/`.
- **M5** — spike workflow + release: CC-220 (corrected), run CC-209 as the first
  `/spike`, v0.3.0 release prep.

Out of v0.3.0: `mcp/` implementation, non-Claude adapters, Night Shift autonomy,
codegraph integration (spiked not built).

### 7. Usability / DX

`pmctl report` morning-report (biggest daily win); `pmctl trace tail` replacing
path-guessing; thinner/cheaper `/pm`; addressable tasks (`pmctl task status
CC-211`); `doctor.sh` extended to the new substrate; spike results stop
evaporating; the doc-freshness gate; `pmctl guard check` unit-testable in
isolation.

### 8. Risks

R1 the rewrite trap (highest — mitigated by M0–M5 + extraction + deferral); R2
touching security-critical guard hooks (every `test-hooks.sh` case must pass
against `pmctl guard check` before hooks thin); R3 schema churn (lock schema in
M1, no behavior depends on it yet); R4 two-language temptation (`pmctl` is bash);
R5 Markdown/JSON boundary thrash (the §2 rule is final); R6 concept-silo creep; R7
the CC-220 sub-agent contradiction; R8 doing M4 before M1–M3.
