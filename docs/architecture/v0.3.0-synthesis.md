# pm-dispatch v0.3.0 — Architecture Restructure: Synthesis

**Status**: planning record — drives the v0.3.0 milestone (epic `CC-211`).
**Date**: 2026-05-22
**Inputs**: three independent architecture plans produced from a shared brief
(`/tmp/arch-plan-brief-v030.md`) — ChatGPT (user-supplied seed), Codex, and
Claude Opus 4.7. Full source plans: [`v0.3.0-source-plans.md`](v0.3.0-source-plans.md).
A fourth input from an AGY CLI was intended but AGY is not yet integrated into the
toolchain — that slot is left open and can be folded in later without reopening
this synthesis.

This document is the authority for the v0.3.0 milestone structure. `MILESTONES.md`
mirrors the M0–M5 breakdown; `BACKLOG.md` carries the individual tickets.

---

## 1. Problem statement

pm-dispatch today is a Markdown-and-Bash config bundle, not a runtime. "Logic"
lives in three places that drift from each other: agent prompt files
(`agents/*.md`), slash-command prose-with-embedded-bash (`commands/pm.md` is the
worst — runtime steps written as English + code), and tested shell (`scripts/`,
`scripts/lib/`).

There is **no state model**. "Tasks" are Markdown rows in `BACKLOG.md`. "Runs" are
`.agent-trace/*.jsonl` files plus a Markdown auto-block in `routing_log.md`.
"Reviews" are timestamped files in `.gate-results/`. Nothing links a backlog
ticket → a dispatch → a gate result → a decision; that chain is reconstructed by
hand every time.

The v0.3.0 goal: restructure toward a **schema-first / state-first / adapter-thin
PM runtime**, and absorb capabilities inspired by four external projects (Multica,
Memori, Superpowers, AI Night Shift) **without** bolting on four feature silos.

---

## 2. Where the three plans converge (treated as settled)

- **Four-layer architecture** — `core/` (data + policy), `runtime/` (the `pmctl`
  spine), `adapters/` (delivery surfaces), `mcp/` (external tool bridge).
- **A state/schema substrate is the real new deliverable** — task / run / event /
  review / decision data models plus a state store. Everything else is refactor.
- **`pmctl` is the runtime spine** — every entry point (slash command, future MCP)
  converges on it; no entry point re-implements logic.
- **MCP must be phased and deferred** — never wrap an unstable `pmctl`.
- **The spike agent must be a planner + main-thread fan-out** — subagents cannot
  spawn subagents; `CC-220`'s original "spike agent dispatches parallel
  sub-agents" wording is structurally impossible and must be corrected.
- **Do not build everything at once** — core + runtime + four adapters + MCP in one
  version is a rewrite disguised as a refactor.

## 5. Recommended v0.3.0 architecture

### 5.1 Four layers (dependency points downward only)

```
adapters/   delivery surfaces — Claude Code today; Codex CLI / MCP later
   │  knows: how one CLI invokes things, how to render output
   │  must NOT know: schema internals, dispatch state transitions, guard rules
   ▼
runtime/  (pmctl) — the spine: task store, dispatch runner, guard engine,
   │               validator, trace logger, report synthesizer
   │  knows: how to mutate state, dispatch, validate, log
   │  must NOT know: that "Claude"/"Codex" exist as products — only an executor profile
   ▼
core/    — pure data + pure policy: JSON schemas, state-machine definitions,
   │       reviewer-policy table, the closed executor enum
   │  knows: nothing executable — definitions only
   ▼  must NOT know: filesystem layout, ~/.claude, any CLI, any process
```

`pm/` (the cross-repo backlog schema) folds into `core/` — it is the same kind of
thing as the task model. The boundary that matters most is **core (data) vs
everything else**; it is enforced by one cheap test (`test-layer-boundaries.sh`:
grep `core/` for forbidden tokens, grep `adapters/` for state-mutation calls).
This is a dependency-direction discipline for future-edit cost, not a
microservice/plugin boundary — collapse a layer if it ever costs more than it
saves.

### 5.2 State / schema substrate (the load-bearing deliverable)

Five entities — the first three are new, the last two formalize what exists:

| Entity | Purpose | Lifecycle |
|---|---|---|
| **Task** | a unit of intended work (runtime representation of a `BACKLOG.md` row) | `open → claimed → in-progress → blocked → done/dropped` |
| **Run** | one dispatch attempt against a Task (wraps a trace + routing-log row) | `pending → dispatched → verifying → ok/partial/failed` |
| **Event** | append-only fact (dispatch started, guard denied, gate verdict, blocker) | append-only |
| **Review** | one gate run's verdict + per-reviewer findings (formalizes `.gate-results/`) | `pending → GO/NO-GO` |
| **Decision** | a sedimented choice (formalizes `DECISIONS.md`) | append-only |

**Markdown-vs-structured rule** (final for v0.3.0): *human-authored → Markdown;
machine-authored → JSONL; never a machine-written Markdown table that something
later parses.* So `BACKLOG.md` / `DECISIONS.md` stay Markdown-primary; Runs and
Events become JSONL; the `routing_log.md` auto-block is promoted to `runs.jsonl`
(the one migration to budget for).

**On-disk layout**: `core/schema/*.schema.json` is version-controlled in-repo;
runtime state lives at `~/.claude/.pm/state/` (per-machine, gitignored —
"definitions in repo, state on disk"); memory cards under
`~/.claude/projects/<id>/memory/` are unchanged. `pmctl` is the **only writer** of
state — no hook, command, or agent writes state files directly.

### 5.3 External-concept mapping (anti-silo: each lands *inside* the substrate)

- **Multica** → defines the **Task/Run lifecycle state machine** in `core/`.
  Blockers become a Task state + Event type. Progress streaming reuses the
  existing `codex-watch.sh` tail. Rejected: Multica's parallel autonomous
  claiming (one orchestrator only).
- **Memori** → defines the **Event log as the memory substrate**. Memory derived
  from what agents *do* (the action stream in `events.jsonl`), not just chat.
  `/mem-distill` gains `events.jsonl` as an input. Rejected: Memori as a separate
  memory engine — it is a lens on the existing four-tier card system.
- **Superpowers** → makes the spec→design→plan discipline (already advisory in
  `commands/pre-impl.md` + `project-pm.md`) a **tiered Task lifecycle gate**
  enforced by `pmctl` — graded by task size (trivial → no gate; small →
  one-line intent; substantial → full `/pre-impl`), mirroring the pr-gate
  express/standard/full tiers, so simple tasks are not over-burdened. Seeds the
  empty `skills/` directory with 2–3 discipline skills. Rejected: building a
  full skill auto-trigger framework.
- **AI Night Shift** → nothing lands in v0.3.0. The continuous-developer /
  heartbeat autonomy loop is rejected (needs unattended dispatch, fights the
  harness lifecycle). The one harvested idea — a `pmctl report` morning-report —
  was deprioritized to `🟢 someday` (CC-236): the maintainer does not run agents
  unattended, so a time-gap roll-up has no current need.

No external project becomes a top-level directory or a per-project slash command.
If a concept cannot land inside the substrate, it is deferred.

### 5.4 MCP — deferred to v0.4.0

v0.3.0 ships only `mcp/README.md` defining the intended tool surface
(`pm_list_tasks`, `pm_create_task`, `pm_dispatch`, `pm_read_trace`,
`pm_guard_check`). That spec is a free, valuable design constraint on `pmctl`:
every `pmctl` subcommand must map cleanly to one MCP tool and support `--json`
output, so a future MCP server is a thin subprocess shell. The MCP server itself
is built in v0.4.0, once `pmctl` is stable and tested.

Ordering principle: *extract cheap shared libs first, define the data contract
second, grow the runtime by extraction third, re-point adapters fourth, add the
new workflows last, defer the speculative.*

| **M1 — State/schema substrate** ★ | `core/schema/*`, re-home `pm/schema.md`, `core/policy/`, `~/.claude/.pm/state/` store, `routing_log.md`→`runs.jsonl` | CC-211 (epic), CC-229, CC-230, CC-231, CC-232 | Every layer references the schema; ships no behavior change — de-risks the substrate before anything depends on it |

## 8. Risks & sequencing hazards

- **R1 — the rewrite trap** (highest): mitigated by the M0–M5 ordering and by
  growing `runtime/` via extraction, not greenfield; MCP + non-Claude adapters
  deferred.
- **R2 — touching the security-critical guard hooks** (M2): every existing
  `test-hooks.sh` case must pass against `pmctl guard check` before the hooks are
  thinned; the engine is proven equivalent before the hook scripts change.
- **R3 — schema churn**: M1 ships the schema with no behavior depending on it yet;
  lock it in M1, treat later changes as a versioned breaking event.
- **R4 — two-language temptation**: `pmctl` is bash. A second language (Node/
  Python) is decided at v0.4.0 for MCP only, and only if SDK ergonomics force it.
- **R5 — Markdown/JSON boundary thrash**: the §5.2 rule is final for v0.3.0;
  `routing_log.md`→`runs.jsonl` is the single budgeted migration.
- **R6 — concept-silo creep**: §5.3 is the contract; M4 forbids new top-level
  directories and per-project slash commands.
- **R7 — the CC-220 contradiction**: correct the ticket to planner +
  main-thread-fan-out before M5 starts.

**Hard sequencing rules**: `test-harness.sh` (M0) before any test-adding work;
`core/schema/` (M1) before `pmctl` (M2); `pmctl` (M2) before thinning
commands/hooks (M3); guard-engine equivalence proven (M2) before hooks thinned
(M3); spike infra (M0) before the spike agent (M5); `pmctl` stable before any MCP
work (v0.4.0).
