# CC-249 — assert_* helper consolidation (spike result)

**Status**: complete
**Date**: 2026-05-23
**Ticket**: BACKLOG.md CC-249

## Investigation scope
- Confirm the current helper surface available in `scripts/lib/test-harness.sh` and determine the canonical `assert_*` API for PR-B.
- Resolve divergent helper definitions across `scripts/test-*.sh`, including `assert_exit` argument order and three-way `assert_contains` behavior divergence.
- Define migration matrix coverage for each consumer script and bound open risks.
- Decide on rollout strategy and sequencing for PR-B without changing public production API behavior outside test infrastructure.

## Angles
- Harness baseline: verify current `scripts/lib/test-harness.sh` exports and confirm it only provides `th_init`, `pass`, `fail`, `run_test`, and `finish` plus report helpers.
- Assertion shape comparison: compare existing `assert_exit` and `assert_contains` variants across test scripts and identify a single consistent API.
- Migration mechanics: assess whether to introduce multi-arity shims or execute break-and-rewrite lockstep across consumers.
- Output checks convergence: align `assert_output_contains` usage with existing string-check behavior and remove duplicate semantics.
- Risk and uncertainty review: inventory scope-out items and follow-up constraints before authorizing PR-B.

## Findings
### Q1_decision
- **Q1_decision**: `assert_exit` unified signature is
  `assert_exit <name> <actual> <expected>` (majority — 4 of 5 files).
  Rationale: minimize call-site churn (4 files keep, 1 file rewrites);
  majority is also the assert-library convention closer to `assertEqual`-
  style where the value-under-test comes first. The one minority file
  (`test-check-docs-freshness`) will be rewritten in PR-B.

### Q2_decision
- **Q2_decision**: `assert_contains` split into THREE separate named helpers, NOT
  a single multi-mode flag helper. Names:
  - `assert_file_contains <name> <file> <literal_substring>` — current
    variant A (6+ files; `grep -Fq`)
  - `assert_file_matches  <name> <file> <regex>` — current
    variant B (2 files; `grep -qE`)
  - `assert_string_contains <name> <haystack_string> <needle>` — current
    variant C (2 files; bash `[[ != *needle* ]]`)
  Rationale: per [[breaking_change_for_maintainability]], a flag-based
  single helper trades 3 readable names for one un-greppable call surface.
  Separate names self-document intent at the call site; cost is one extra
  definition in the harness, paid once.

### Q3_decision
- **Q3_decision**: Migration strategy is BREAK-AND-REWRITE. No multi-arity
  shim, no deprecation period. All consumer files updated in PR-B in lockstep with
  the harness. Rationale: shim doubles harness surface and hides the very
  divergence CC-249 closes; per [[breaking_change_for_maintainability]] user
  prefers full breaking schema changes; this is internal test infra, not a public
  API, so blast radius is bounded to the repo.

### Q4_decision
- **Q4_decision**: `assert_output_contains` is MERGED INTO
  `assert_string_contains` at the call site. The two existing implementations
  differ only in whether `$LAST_OUTPUT` is implicit (`test-check-docs-freshness`) or
  explicit-arg (`test-patch-gitignore`); the explicit-arg form wins for PR-B
  (no hidden global), so callers that relied on the implicit `$LAST_OUTPUT` must
  pass `"$LAST_OUTPUT"` explicitly. Net effect: `assert_output_contains` is deleted;
  both consumers call `assert_string_contains` instead.

### Q5_uncertainties
- **U1 (test-hooks.sh tail unread):** RESOLVE in PR-B — re-grep the full file as
  the first PR-B audit step; if additional assert_* defs are found, add them to the
  migration matrix before any consumer rewrite.
- **U2 (test-commands.sh regex intent):** SCOPE-OUT of this spike; treated as
  "callers using regex semantics get assert_file_matches, callers using literal
  substrings get assert_file_contains"; PR-B decides per-call-site at audit time, NOT
  in spike.
- **U3 (test-lint-frontmatter.sh custom helpers run_ok/run_fail/run_exit):**
  SCOPE-OUT — outside `assert_*` convention; file separate ticket only if PR-B
  audit shows they overlap with the new assert_* surface.
- **U4 (test-patch-gitignore.sh side-by-side dup):** RESOLVED by Q4 above
  (merge collapses the dup).
- **U5 (test-run-all-tests.sh meta-runner):** SCOPE-OUT — it orchestrates suites,
  doesn't run test logic; no assert_* of its own to migrate; its
  `assert_contains` (variant C, string-form) gets renamed per Q2.

## Amendment 2026-05-24 — gap surfaced during PR-B.2 (CC-254)

The spike's Q1-Q5 design decisions answered the WHAT (API shape, naming, semantics) but not the HOW (does this API replace the existing usage cleanly?). PR-B.2 dispatch on 2026-05-24 surfaced a hidden contract conflict the spike did not catch:

**The gap**: All 13 consumer test scripts follow the pattern `assert_X "$name" ...; pass "$name"` — `assert_*` is treated as a check, the consumer separately calls `pass` to increment the PASS counter. The spike enumerated helper DECLARATIONS but never inspected consumer CALL-SITES; PR-B.1 (#148) therefore shipped helpers that auto-called `pass` on success — and pure rename in PR-B.2 would have caused double PASS counting.

**Symptoms**: PR-B.2 dispatch hit timeout 124; codex defensively shadowed the harness by re-defining the 4 helpers locally in 9 of 13 consumer files (violating Q3 "no shim, no deprecation"); 9 apply_patch failures across 4 complex files.

**Recovery**: CC-254 PR amended PR-B.1 to remove auto-pass from the helpers; PR-B.2 will re-dispatch as pure rename without the double-count risk.

**Lessons captured for future spikes** (now in `agents/project-pm.md` + memory):
- `[[feedback_spike_pilot_required]]` — every API-design spike MUST include a `## Pilot walkthrough` section: pick 1 representative consumer, write the verbatim before/after diff applying every spike decision. If the walkthrough can't be written cleanly, the spike's API decision is not yet mature.
- `[[feedback_explore_call_site_context]]` — Explore symbol surveys must capture BOTH declarations AND call-site context (raw line + 2 before/after). Declaration-only surveys miss usage-pattern conflicts.
- Additive-PR pilot rule — every PR shipping a new API must migrate at least 1 real consumer in the SAME PR.
