# CC-440 — `/ship` 並行版可行性（spike result）

**Status**: complete
**Date**: 2026-07-03
**Ticket**: BACKLOG.md CC-440

## Investigation scope

`/ship`（單票版，CC-439）已合併，主線程一次跑一張票、實作留在主線程直接改、分支用普通 `git checkout -b`。
真正的槓桿是「同時跑 N 張票」，但這疊加了兩個核心假設變化：(1) 實作要從主線程直接改換成 dispatch 給
executor；(2) 分支要從 `git checkout -b` 換成 `pmctl worktree create`（CC-014）避免 N 條 pipeline
互踩同一個工作目錄。BACKLOG.md 列出四個要收斂的問題（外加討論過程中額外浮現的 git 鎖疑慮），本輪直接
與使用者逐題討論收斂，不做多角度 fan-out（單一使用者對照四題的判斷已足夠明確，不需要外部視角）。

## Decisions

| # | 問題 | 決策 |
|---|---|---|
| Q1 | lane 失敗隔離：一條 pipeline（worktree+dispatch+gate）失敗時，其他 lane 是否需要感知/暫停？回報機制長什麼樣？ | **互不干擾，逐條即時通知**——各 lane 完全獨立執行，任一 lane 卡住/失敗時立刻通知使用者，不等其他 lane 跑完再彙總，也不因為一條失敗而暫停其他 lane。 |
| Q2 | gate 迴圈的人機分工：實作換成 dispatch 給 executor 之後，NO-GO fix-loop 由誰驅動？ | **executor 自扛迴圈到卡住才喚醒使用者**——dispatch brief 把整個 fix-loop（讀 gate 結果、判斷、修改、重跑 gate）交給 executor 自己跑，主線程不逐輪介入；只有 executor 判斷自己卡住（同一 finding 反覆修不掉、或遇到需要人類決策的根本性分歧）時才喚醒使用者。 |
| Q3 | worktree 生命週期：`pmctl worktree create/remove/gc` 在多條並行 lane 下的 create/remove 時機？ | **等使用者確認合併後才 remove**——GO 之後仍保留 worktree，直到使用者手動確認合併對應 PR，才觸發 `pmctl worktree remove`。這是最保守但佔用磁碟時間最久的選項；換取的是合併前隨時可以回頭檢視/追加修改該 lane 的工作目錄。 |
| Q4 | 併發上限：N 的合理上限，以及是否需要像 `--parallel` gate 一樣的 reviewer 隔離考量？ | **N 為可調參數，天生結構隔離，不做選票/仲裁機制**——N 沒有寫死的上限，由使用者依機器負載自行調整；reviewer 隔離不需要額外機制，因為每條 lane 已經在獨立 `pmctl worktree` 目錄下執行，gate 產出的 artifact 又存在 out-of-repo state store（依 `run_id` 分區），結構上天然不共用資源。若未來實測發現真的資源耗盡（例如同時太多 codex process 佔滿機器），視為「N 設太高」的訊號，屬於使用者調參／未來 backpressure follow-up 票的範圍，不在本次 spike 設計內。 |
| 附加 | 討論過程中額外浮現的疑慮：N 條 lane 各自獨立 worktree，但共享同一個 `.git` 物件庫，會不會有寫入衝突？ | **不需要自訂鎖，只需在並行執行期間關閉 `git config gc.auto 0`**。分析：git 物件是 content-addressed，同一物件被兩邊各自寫出的 bytes 相同，不會壞；每條 lane 用不同分支，不會撞到同一個 ref 鎖檔。真正有極小衝突窗口的是 `packed-refs` 重寫（若某條 lane 觸發 auto-gc、同時另一條 lane 在 create/remove worktree）——用關閉 auto-gc 規避即可，不需要一整套鎖機制。真正需要序列化的只有兩處，且都已有現成方案：`pmctl worktree create/remove/gc` 本身的 manifest 寫入（已有 lock，見 `using-git-worktrees.md`）、以及最終 PR 合併回 main（本就是 human-in-the-loop，天然序列化）。 |

## Recommendation

四個問題（外加 git 鎖疑慮）都已收斂到可執行的設計決策，滿足 BACKLOG.md 的 Done-when 條件，可以開一張明確
的實作票（承接 CC-439，範圍：N-lane orchestrator，把上述五項決策落地）。

實作範圍建議切分：

1. Orchestrator 主迴圈：讀入 N 張票的清單 → 對每張票 `pmctl worktree create` → 產生 dispatch brief（把
   fix-loop 責任交給 executor，如 Q2）→ `pmctl dispatch run --lifecycle detached` 平行送出。
2. 執行前置：orchestrator 啟動時先用 `git config --get gc.auto` 讀出目標 repo 現有值，**並記錄該 key 原本
   是否存在**（存在則暫存實際值；不存在則記為「未設定」，不要用 git 預設 `256` 頂替），再寫入
   `git config gc.auto 0`。orchestrator 主迴圈結束時（不論全部 lane 成功、部分失敗、或整批被中斷）一律
   還原：原本有設定就寫回暫存值，原本未設定就 `git config --unset gc.auto` 移除這個 key，**不可寫回
   `256`**——把「未設定」還原成「顯式設定 256」表面上語意接近，實際上是永久污染了 repo 的 local config，
   跟「還原」的定義矛盾。這是一個 orchestrator 自己啟閉的暫時性 repo config 覆寫，生命週期跟本次並行
   執行綁定，不是永久設定。
3. 失敗回報：每條 lane 各自的 dispatch/gate 狀態變化即時推播給使用者（Q1），不等其他 lane。
4. worktree 保留策略：GO 之後不自動 remove，等使用者明確確認合併 PR 才觸發 `pmctl worktree remove`
   （Q3）——需要一個追蹤「哪些 lane 已 GO 但未合併」的清單機制，避免累積孤兒 worktree（可搭配既有
   `pmctl worktree gc --dry-run --merged` 定期盤點）。
5. N 不做程式碼硬上限，僅在文件/CLI help 提醒使用者依機器負載自行調整（Q4）。

## Open risks

- Q3（等使用者合併才 remove）會讓多條並行 lane 同時佔用磁碟空間偏久；若使用者常態性同時跑大量 lane，
  可能需要之後補一個「GO 太久未合併」的提醒機制（本次 spike 範圍不含）。
- Q1 的「逐條即時通知」在 N 很大時可能造成通知轟炸；本次未定案通知節流策略，留給實作票視實測情況決定。
- git 鎖分析僅基於 git 物件模型的理論推導，未實測 N 條 lane 真正並行 commit/push 時是否會踩到未預期的
  邊界情況（例如 hook 觸發、CI 同時跑多條 pipeline）；建議實作票的第一步先用 2-3 條 lane 做小規模驗證，
  而非直接開到大 N。
