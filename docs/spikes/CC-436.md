# CC-436 — codex-host PreToolUse payload 驗證 probe（spike result）

**Status**: complete
**Date**: 2026-07-06
**Ticket**: BACKLOG.md CC-436

## Investigation scope

[[CC-381]] spike（`docs/spikes/CC-381.md`）用唯讀證據（`codex features list`/`codex doctor --json`/binary
字串反查）確認 codex `PreToolUse` hook 是 stable feature 且應該 fail-closed，但沒有實際跑過一次
end-to-end 阻擋，也不知道 payload 欄位能否映射到 `pmctl guard check --file/--command`。本票是 CC-381
收斂矩陣認定的「第一刀」：唯讀 probe，不動 `install.sh`/`doctor.sh` write path。

**方法**：在 `/tmp/cc436-codex-home` 建 throwaway `CODEX_HOME`（複製既有帳號 `auth.json` 以取得真實
API 認證，其餘設定全新），對一個 throwaway repo（`/tmp/cc436-repo`）跑 `codex exec`，分別觸發：
1. 一個明確 shell command（`echo blocked`）
2. 一個檔案寫入動作（透過 `apply_patch` 建立 `probe.txt`）

hook 腳本把收到的 stdin JSON payload 全文記錄到檔案，再回傳 deny 決策，藉此同時驗證「payload 長什麼樣」
與「deny 是否真的 fail-closed」。

## Findings

**1. Hook 設定格式與 Claude Code 相容，不是獨立 schema。**
codex 不是用 `~/.codex/config.toml` 的 `[hooks]` table（那個猜測格式被 `--strict-config` 接受但從未
生效，純屬巧合通過而非真實欄位），而是讀取 `$CODEX_HOME/hooks.json`，格式與 Claude Code 的
`settings.json` hooks 區塊一致：

```json
{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Bash",
        "hooks": [{"type": "command", "command": "/path/to/hook-script.sh"}]
      }
    ]
  }
}
```

省略 `matcher` 欄位＝比對所有 tool（驗證於 apply_patch 觸發時的設定）。deny 決策透過 hook 腳本 stdout
回傳 `hookSpecificOutput.permissionDecision: "deny"`（同樣是 Claude Code 相容格式）。

**2. Fail-closed 屬實，兩種動作都在 end-to-end 測試中被真的擋下。**
- Command 阻擋：`echo blocked` 被擋，`codex` CLI 輸出 `Command blocked by PreToolUse hook: ...`，
  模型收到阻擋訊息作為 tool result，沒有繞過。
- File-write 阻擋：`apply_patch` 建立 `probe.txt` 被擋，事後確認 `probe.txt` 檔案**確實不存在**於
  target repo（不是回報阻擋但底層仍寫入的假陽性）。

**3. Payload 欄位對照 `pmctl guard check` 需求——command 動作足夠，file 動作有缺口。**

Bash/command 動作 payload（欄位齊全，可直接映射）：
```json
{
  "session_id": "...", "cwd": "/tmp/cc436-repo",
  "hook_event_name": "PreToolUse", "tool_name": "Bash",
  "tool_input": {"command": "echo blocked"},
  "tool_use_id": "call_..."
}
```
`tool_input.command` + `cwd` 直接映射到 `pmctl guard check --command "<command>"`（在 `cwd` 下執行）。

`apply_patch`（檔案寫入）動作 payload（**缺口**）：
```json
{
  "tool_name": "apply_patch",
  "tool_input": {
    "command": "*** Begin Patch\n*** Add File: probe.txt\n+hello\n*** End Patch\n"
  }
}
```
沒有獨立的 `file_path` 欄位——目標路徑（`probe.txt`）內嵌在 unified-diff 風格的 patch 文字裡
（`*** Add File: <path>` / `*** Update File: <path>` / `*** Delete File: <path>`），必須自行解析
patch 文字才能取得可傳給 `pmctl guard check --file <path>` 的路徑。這與 command 動作的乾淨欄位形成
明顯落差，直接限制了 codex-host guard binding 在檔案層面的設計空間：任何 host manifest
（[[CC-438]]）若要做 file-path 級別的 guard binding，都必須內建一個 `apply_patch` 文字 parser，
不能假設有現成的 `file_path` 欄位可用。

**4. Hook trust gate 在非互動 `codex exec` 下會無限期掛起，不是 fail-closed 拒絕。**
不帶 `--dangerously-bypass-hook-trust` 執行同一個 hooks.json 設定，`codex exec` 卡住不動（60 秒
timeout 後仍無任何 hook 觸發輸出、payload 也未寫入），推測是等待一個互動式「trust this hook？」
提示，headless 環境無法回應。反查 binary 沒有找到任何 trust 狀態持久化檔案或 `codex hooks trust`
之類的 CLI 子命令——這意味著 headless dispatch 路徑（`pmctl dispatch run --adapter codex`）目前
**沒有除了 `--dangerously-bypass-hook-trust` 之外的方式**讓 hook 生效；不帶這個 flag 會直接卡死
整條 dispatch pipeline，而不是優雅地跳過 hook。

## Recommendation

**Adopt，但範圍收斂為「command-level guard binding 優先，file-level 需要額外 parser 投入」**：

1. Payload 驗證通過，可以往 [[CC-438]]（host manifest schema v1）推進，但 schema 設計要顯式區分
   command 動作（可直接映射）與 file 動作（需 patch-text parser）兩種 `guard_bindings` 覆蓋度，
   不能假設兩者對稱。
2. `hosts/codex/host.yaml` 的 hook 設定產出品應該直接寫 Claude-Code-相容格式的 `hooks.json`，
   不是獨立 codex schema——這降低了未來維護面（同一份 hook script 邏輯理論上可能被 claude-host 與
   codex-host 共用，值得在 [[CC-438]] schema 設計時評估）。
3. **`--dangerously-bypass-hook-trust` 必須是 codex-host dispatch 路徑的必要參數，不是可選項**——
   否則 hook 完全無法在 headless 場景生效（會掛起而非跳過）。這個 flag 名稱雖然標「dangerous」，
   但在 PM 自己產出/自己信任的 hooks.json 場景下語意上其實是「headless 环境的必要條件」而非真的
   繞過陌生風險；[[CC-438]] 的文件應該解釋這個語意落差，避免未來維護者誤解為降低安全性。
4. 沿用既有 `write_guard_mode: cli-only` 當 fallback——native hook 是防禦縱深的加分項，不是取代
   PM 端既有 brief-level 靜態分析。

## Open risks

- file-path 解析器本身是一塊未評估的實作成本：`apply_patch` 文字格式需要覆蓋 Add/Update/Delete
  File 三種 header，以及 codex 是否有其他檔案寫入路徑（例如透過 Bash 的 `cat > file` 重導向）
  ——後者其實仍走 `tool_name: "Bash"`，不會觸發獨立的 file-path 判斷，這代表 file-level guard
  binding 天生無法涵蓋「透過 shell 重導向寫檔案」的路徑，只能靠 command-level guard 攔（例如擋
  `cat > /etc/passwd` 這種寫入目標敏感路徑的 command pattern）。
- hook trust gate 的掛起行為只在本次 60 秒 timeout 內觀察到「無輸出」，未進一步反查是否有更長的
  內建 timeout 或最終會 fail-open/fail-closed——若未來 `pmctl dispatch run` 真的要接上 codex-host
  hook，需要額外驗證「忘記加 `--dangerously-bypass-hook-trust`」時的最終行為，避免 CI/dispatch
  流程無聲卡死超過既有 timeout 假設。
- opencode 作為第三個 host，其設定面（`opencode.json`）尚未做同等的 payload 驗證，[[CC-448]]
  probe 需要獨立驗證，不能假設 opencode 的 hook payload（若存在）與 codex 這裡的欄位對稱。
