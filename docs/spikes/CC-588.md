# CC-588 — codex reviewer sessions vs. AppContainer/MSYS2 CreateFileMapping (spike result)

**Status**: complete
**Date**: 2026-09-22
**Ticket**: BACKLOG.md CC-588

## Investigation scope

1. Is the `CreateFileMapping` Win32 error 5 that blocks qa-tester reviewer
   sessions during `pr-gate` on native Windows actually a concurrency race
   (as originally filed in issue #609, "parallel mode concurrent bash.exe
   race"), or something else?
2. Has anyone outside this repo hit the same failure, and if so what is the
   documented mechanism and remedy?
3. Does closing this gap require a pm-dispatch architecture change, and if
   so, what are the realistic options and their costs — is a redesign
   actually justified given the repo's existing Windows-support posture?

## Angles

### a1 — Re-testing the "concurrency race" hypothesis

Issue #609 was originally filed against `--mode parallel` (concurrent
reviewer bash.exe cold starts). Two direct counter-tests were run this
session against PR #611:

- The same failure reproduced under `--mode sequential` — a single reviewer
  session, zero sibling reviewer concurrency.
- A second hypothesis (that the *orchestrating* Claude Code session's own
  polling — `ScheduleWakeup` + `pmctl artifacts show` calls — was adding
  concurrent bash.exe pressure) was tested and falsified: a strict
  zero-polling run (`gate run` + a single backgrounded `gate wait`, no
  interim checks) hit the identical error, at the same point in dispatch.

Conclusion: not a race condition. The failure is deterministic given a
particular AppContainer token's access grant, not a function of how many
bash.exe processes are alive at once.

### a2 — External corroboration and root-cause mechanism

Web research surfaced the same failure class in three independent projects:

- [openai/codex#12000](https://github.com/openai/codex/issues/12000) — codex
  itself hits the identical `CreateFileMapping` error running `git` inside
  its own non-interactive Windows sandbox automation. Open, unresolved, no
  documented workaround.
- [microsoft/mxc#1061](https://github.com/microsoft/mxc/issues/1061) —
  detailed technical mechanism: MSYS2/Cygwin runtime init calls
  `NtCreateDirectoryObject` with an absolute NT path under the global
  `\BaseNamedObjects\msys-2.0S5-<hash>` namespace. AppContainer's
  named-object redirection operates only at the Win32 API level; the raw NT
  syscall bypasses it and hits the real global namespace, where the
  AppContainer token lacks `DIRECTORY_CREATE_SUBDIRECTORY` access. Described
  as a hard architectural limitation — "no filesystem, capability, or UI
  setting can grant it" from outside the sandboxing implementation itself.
- [finogeeks/finsafe#34](https://github.com/finogeeks/finsafe/issues/34) and
  [#38](https://github.com/finogeeks/finsafe/issues/38) — a different
  sandboxing tool hitting the same MSYS2-under-restricted-token class of
  failure.

Conclusion: this is a known, cross-project, currently-unresolved
AppContainer/MSYS2 incompatibility — not something specific to pm-dispatch's
dispatch logic, and not fixable by changing how pm-dispatch invokes codex.

### a3 — Why this hits qa-tester specifically

`runtime/bin/pr-gate.sh`'s QA execution helper mechanism
(`qa_execution_prepare()` / `qa-test-attempt-*.sh`, ~line 1839) instructs the
qa-tester reviewer to invoke a host-generated helper script via
`timeout --kill-after=15 N -- <command>` from *inside its own codex session*
for supplemental test runs. That session already runs inside codex's
`workspace-write` sandbox (an AppContainer token on native Windows). Any
`bash.exe` spawned in that nested chain (codex's sandboxed shell wrapper →
helper script → `timeout` → the actual test invocation) hits the same wall.
The other three reviewers (critic, architecture-reviewer, security-reviewer)
don't invoke this mechanism and are unaffected — consistent with every
observed failure being qa-tester-specific.

### a4 — Is the sandbox-relaxation escape hatch available?

`adapters/codex/dispatch.sh` (~line 288) deliberately and permanently rejects
`--sandbox danger-full-access` at a single chokepoint, for security reasons,
with no configuration path around it. Reopening it to work around this bug
would let a reviewer agent run with unrestricted machine access — a real
security regression, not a fix, and not a decision to make unilaterally
inside a bug investigation.

### a5 — Architecture options, weighed against existing repo posture

Per `DECISIONS.md` 2026-06-13 (`defer-native-windows-support-during-core-dev`)
and its 2026-09-01 amendment (`windows-git-bash-experimental-local-use-exception`):
native Windows Git Bash is a **bounded experimental local-use exception**.
CI and release sign-off remain Linux/WSL2 only; Windows is explicitly *not* a
release-qualification platform. This bug only affects local `pr-gate` runs on
native Windows — it has zero effect on CI, on Linux/WSL2 users, or on any
other reviewer.

Options considered:

- **(A) Move QA test execution outside the reviewer's own sandbox.**
  `pr-gate.sh` (unsandboxed, host-side) would run the actual test commands
  itself and hand qa-tester only the resulting evidence file to read and
  judge, instead of letting qa-tester invoke bash itself. This is the only
  option that actually removes the failure class. Cost: a real protocol
  redesign — either the test plan must be decided before dispatch (loses
  qa-tester's live judgment of what to test against the diff), or a
  two-phase propose→execute→resume interaction is needed, which doesn't
  exist today for reviewer sessions (only detached `gate wait` has
  session-continuation machinery). Not a small patch.
- **(B) Grant the AppContainer token the missing namespace rights.** Per a2,
  described upstream as not achievable from outside the sandboxing
  implementation itself — no capability SID exists for this. Not actionable
  from pm-dispatch; the only real lever here is the already-filed upstream
  issue (openai/codex#12000).
- **(C) Run the QA helper via a non-MSYS2 shell (native PowerShell/cmd)
  instead of bash.** Avoids the `\BaseNamedObjects\` dependency entirely, but
  the whole test suite and runtime (`tests/shell/*.sh`, `runtime/lib/*.sh`,
  `cli/pmctl`) is bash-authored; porting the QA invocation path means either
  an ongoing dual-maintenance translation burden, or shelling back out to
  WSL2 (a dependency this repo doesn't currently require or support per
  `docs/platform-support.md`). Disproportionate to the benefit.
- **(D) Bounded automatic retry.** Since a1 shows the failure isn't reliably
  reproducible per session (roughly half of ~6 `pr-gate` attempts on PR #611
  hit it, the other half didn't, and every attempt that got past dispatch
  produced a clean 3/4-reviewer approval), a single automatic re-dispatch of
  just the failed reviewer, on this specific error signature, would recover
  most of the observed cost cheaply — without touching the dispatch
  protocol. Doesn't eliminate the failure class, just amortizes it.

## Findings

- Confirmed structural, not racy: reproduces under zero concurrency, in both
  sequential-mode and zero-polling configurations.
- Confirmed externally corroborated: identical failure in codex's own
  Windows automation (openai/codex#12000) and precisely explained at the
  Windows API level (microsoft/mxc#1061), with a third project
  (finogeeks/finsafe#34/#38) hitting the same MSYS2-under-restricted-token
  class of bug.
- Confirmed no workaround exists inside pm-dispatch's current design: the
  one sandbox-relaxation escape hatch is deliberately and permanently closed
  (a4), and no capability grant is available from outside codex's sandboxing
  implementation (a2).
- Confirmed practical impact is real but bounded: across ~6 `pr-gate`
  attempts on PR #611 (mixing sequential/parallel, with/without polling),
  roughly half completed cleanly on the first try; every attempt that landed
  produced a consistent, clean 3-approve/1-environment-blocked-or-approved
  result — never a genuine code-quality disagreement, and the finding's own
  `origin` field was always "uncertain," never "diff_caused." No attempt
  failed to *eventually* land.
- Confirmed this only affects native-Windows local `pr-gate` runs — CI and
  Linux/WSL2 users are unaffected, and the repo's own platform-support
  decision (`DECISIONS.md` 2026-09-01) already scopes native Windows as
  bounded/experimental/non-release-qualifying.

## Recommendation

**Defer** option (A), the only real architectural fix (host-side QA
execution, reviewer-protocol redesign). The repo's own committed posture
(CC-370 / `DECISIONS.md` 2026-09-01) already treats native Windows as a
bounded experimental local-use exception, not a fully supported platform —
investing in a reviewer-dispatch protocol redesign to fully close a gap that
is native-Windows-local-only, non-blocking (every affected gate eventually
landed), and does not touch CI is disproportionate to that stated scope
right now. Revisit if either (a) native Windows moves out of the
experimental-exception posture, or (b) the failure rate materially worsens
past the "roughly half, always eventually recovers" pattern observed here.

**Reject** option (B) as not actionable from pm-dispatch (track only via the
upstream issue) and option (C) as disproportionate (a platform-support
commitment — WSL2 or dual-shell maintenance — far larger than the problem
it solves).

**Adopt (as a separate, cheap follow-up, not part of this spike)**: option
(D), a bounded single-retry of just the failed reviewer when `pr-gate.sh`
detects this specific error signature, surfaced explicitly as an
"environment retry" (never rendered as a `Final: NO-GO` or confused with a
real reviewer finding). This is scoped small enough to be its own ticket
rather than bundled into this spike's closure.

## Open risks

- The "roughly half" failure rate is drawn from a single PR's ~6 attempts on
  one machine, not a controlled sample — it is directionally useful, not
  statistically solid. If a future measurement shows it materially worse,
  the "defer (A)" call above should be revisited.
- No visibility into whether/when upstream (openai/codex#12000) will be
  fixed; that would remove the problem for free but isn't something to plan
  around.
- Option (D)'s retry only helps when the error is transient per-invocation;
  if a given AppContainer token instance never gets namespace access for the
  lifetime of a session (vs. varying per bash.exe cold start within it), a
  same-session retry could still fail deterministically. Not verified either
  way in this spike — worth confirming empirically before implementing (D).
