# CC-471 — codex `pm_command_interface` probe（spike result）

**Status**: complete
**Date**: 2026-07-09
**Ticket**: BACKLOG.md CC-471

## Investigation scope

[[CC-445]] shipped the codex-host command-guard write path (opt-in
`--enable-codex-command-guard`), but `hosts/codex/host.yaml`'s
`pm_command_interface` capability was left `confidence: assumed` — nobody
had actually verified whether the codex CLI can host a `/pm`-equivalent
entry point the way `commands/pm.md` does for Claude Code. This spike
closes that gap with a real end-to-end functional + manual smoke pass on
the `feat/CC-445` branch (post round-21 GO), then answers the actual
question: can codex run pm-dispatch's PM orchestration natively?

## Method

1. Focused test suites: `scripts/test-host-write-codex.sh` (31),
   `scripts/test-pmctl-guard.sh --filter pm-prebash` (7),
   `scripts/test-doctor.sh --filter codex` (12),
   `scripts/test-guards.sh --filter pm-bash` (84).
2. Full suite: `scripts/run-all-tests.sh` (72 passed, 0 failed, 0 skipped).
3. Manual smoke with a throwaway `CODEX_HOME`: install the hook, confirm
   `pmctl doctor` reports the codex host as wired, then feed hook payloads
   directly (`ls` → allow, `rm -rf ...` → deny).
4. Real end-to-end smoke: briefly wire the guard into the real
   `~/.codex/hooks.json` and run real `codex exec` —
   - allow path: codex ran `printf codex-host-smoke` via Bash successfully.
   - deny path: codex attempted
     `rm -rf /tmp/pm-dispatch-codex-host-deny-nonexistent`, blocked by the
     `PreToolUse` hook.
   - Removed the real hook afterward with `scripts/uninstall-guards-codex.sh`;
     `pmctl doctor` confirmed it returned to the unwired default. The real
     run produced install/uninstall backup files under `~/.codex/hooks.json.bak.*`
     (the installer's normal safety behavior); repo `git status` stayed clean.

## Findings

**1. The command-guard write path works exactly as designed, no functional
issues found.** All focused suites, the full suite, the manual payload
smoke, and the real `codex exec` allow/deny smoke all passed. This is a
functional confirmation of round-21's GO verdict, not a new finding about
guard correctness.

**2. codex has no native equivalent of Claude Code's Agent/subagent
invocation — `pm_command_interface` is genuinely unsupported, not just
unevaluated.** Claude's `/pm` (`commands/pm.md`) works by invoking
`project-pm` via the `Agent` tool: a live, in-conversation subagent call
that can pause, ask the user a clarifying question (`AskUserQuestion`),
and resume — the entire discovery/dispatch/gate routing in
`agents/project-pm.md` depends on that interactive loop. codex CLI has no
equivalent tool-call surface for a host session to open a subagent and
exchange turns with it. What codex *can* call is the lower-level CLI
surface that already exists independent of any host-side orchestration
layer:

```
pmctl dispatch run --adapter codex --cd <repo> --brief-file <brief>
pmctl dispatch wait <run_id> --cd <repo>
pmctl gate run --executor codex --cd <repo>
pmctl context query <repo> --source memory -- <query>
pmctl memory doctor
```

None of these give codex a `/pm`-shaped entry point; they are the same
`pmctl` primitives any script or human could already call. A codex-hosted
session today can: (a) have Bash calls guarded by the round-21 hook, and
(b) drive dispatch/gate primitives directly, but it cannot say `/pm <request>`
and get the same triage/routing behavior Claude's `/pm` provides.

**3. Closing the gap requires a new orchestration surface, not more host
wiring.** Two shapes were considered:

- **CLI-native (`pmctl pm ...`)**: move the orchestration logic in
  `commands/pm.md` (snapshot capture, handover validation, dispatch/wait
  loop, discovery routing) into `pmctl` itself, so both Claude's `/pm` and
  a codex host call the same CLI surface.
- **codex-native prompt file** (e.g. a `hosts/codex/commands/pm.md` fed to
  `codex exec` as a system/brief, mirroring `agents/project-pm.md`): keeps
  the orchestration logic host-specific, parsed from PM's own text output
  after the fact.

The CLI-native shape is structurally preferable — it gives Claude and
codex one shared implementation instead of two parallel ones that will
drift (the same concern `architecture-reviewer` raises whenever a
host-specific branch appears in core). But it cannot achieve feature
parity: `codex exec` is a one-shot headless call with no mechanism to
pause mid-run and ask the human a clarifying question the way
`AskUserQuestion` does inside Claude Code. A `pmctl pm` surface for codex
would necessarily be a reduced, batch-only mode (accept one fully-formed
request, return one handover/result) — that reduction needs to be an
explicit, declared limitation, not something discovered later as a
feature gap.

## Recommendation

**Adopt CLI-native (`pmctl pm`), scoped and declared honestly**:

1. Update `hosts/codex/host.yaml`'s `pm_command_interface` capability from
   `confidence: assumed` to `confidence: probed`, `provider: none` (probed
   absence, not silent gap — same honesty pattern the schema already uses
   for `file_guard`).
2. Plan `pmctl pm` as a new ticket ([[CC-473]]) with an explicit, stated
   scope boundary: batch-only orchestration (no live clarification loop)
   for non-Claude hosts, with Claude's own `/pm` free to keep using the
   richer `Agent`/`AskUserQuestion` path on top of the same underlying
   `pmctl pm` primitives where they overlap (snapshot capture, handover
   validation, dispatch/wait sequencing).
3. Do not attempt a codex-native prompt-file shape (`hosts/codex/commands/pm.md`)
   as a competing surface — it would duplicate orchestration logic in two
   places and is exactly the drift architecture review flags.

## Open risks

- `pmctl pm`'s batch-only mode means any request that would trigger
  Claude's `/pm` uncertainty routing (discovery fan-out, ambiguous scope
  questions) needs a defined non-interactive fallback for codex (e.g.
  default to the most conservative route and report why, rather than
  blocking on a question nobody can answer).
- opencode's `pm_command_interface` is a separate, still-unevaluated
  question — do not assume codex's "no native subagent" finding transfers;
  [[CC-448]]'s own host probe should confirm or refute it independently.
