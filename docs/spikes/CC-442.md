# CC-442 — 統一 `pmctl ship <ticket-id>` 單一入口 (spike result)

**Status**: complete
**Date**: 2026-07-04
**Ticket**: BACKLOG.md CC-442

## Investigation scope

Three open architecture decisions blocking a real implementation ticket:

1. **Finish call-shape**: in single-ticket in-place/`--worktree` mode, should
   the Step-2-implementation → gate+PR call reuse the existing
   `pmctl ship finish`, or converge into the same unified entry point (e.g.
   `pmctl ship <ticket-id>` called a second time, or a distinct sub-action)?
2. **Tracking/marker schema**: after `--adapter` forces `--worktree`, do
   non-dispatch `--worktree` lanes need their own tracking record (e.g. an
   entry in `ship-parallel.jsonl`), or does `pmctl worktree create`'s own
   manifest already cover that case?
3. **Pilot walkthrough**: migrate the existing `pmctl ship --parallel`
   consumer to call the unified single-ticket entry point and produce a
   verbatim before/after diff, to confirm the design is clean and
   shim-free.

## Angles

### a1 — Entry-point call-shape convergence (finish call-shape)

Read `scripts/lib/pmctl-ship.sh` (`pmctl_ship_prepare`, `pmctl_ship_finish`),
the `cli/pmctl` ship routing block, and `commands/ship.md` (the CC-439
`/ship` contract). Drafted two options:

- **Option A** — keep `pmctl ship finish <id>` as a separate, unchanged
  verb.
- **Option B** — converge `finish` into the same entry point (state-detect
  prepare vs finish from repo state, or a second `pmctl ship <id>` call).

Found `finish` is already a hardened, allowlisted, load-bearing primitive:
branch-identity guard, `gh` preflight, pre/post-gate HEAD-drift guard, the
`.pm-dispatch-ship-finish.json` marker, and a Bash-allowlist entry
(`pmctl ship finish:*`) that pre-approves the whole command for
headless/unattended executors — this is exactly how `--parallel` lanes
dispatch the gate+PR step today. `--worktree`/`--adapter` are semantically
inert at finish time (worktree already exists, operates on `--cd
<work_dir>`; gate executor is hardcoded `--executor codex`). Option B's
state-detection is the "guard-one-execute-another" anti-pattern the
v0.6.0/v0.7.0 detached-supervisor lesson explicitly warns against — an
explicit verb is a trusted scalar, state-inference against a possibly-stale
worktree is not. Option A also never touches the CC-439 `/ship` contract:
`commands/ship.md` never calls `pmctl ship finish` at all — Steps 3/4 inline
`pmctl gate run` + `git push` + `gh pr create` directly; `finish` is a
parallel, scriptable bookend for the orchestrator, not something `/ship`'s
prose flow depends on.

### a2 — Tracking/marker schema audit

Read `scripts/lib/pmctl-ship-parallel.sh` (tracking append/refresh/status/
list, the `ship-parallel.jsonl` line schema:
`{ticket, branch, path, run_id, status, created_ts}`) and
`scripts/lib/pmctl-worktree.sh` (the worktree manifest schema:
`{slug, branch, path, created_ts}` — no ticket, no run_id, no ship status,
no adapter).

Findings:

- Empty/absent `run_id` does **not** break anything —
  `_pmctl_ship_parallel_lane_status` checks the
  `.pm-dispatch-ship-finish.json` marker file unconditionally first,
  regardless of `run_id`; only falls through to
  `dispatch_record_read_state` (which fails closed on empty `run_id`) if the
  marker is absent, printing a harmless `"running"` placeholder in that
  case.
- The worktree manifest alone is **not** sufficient: `ship status`/
  `ship list` read only `ship-parallel.jsonl`, never
  `pmctl_worktree_manifest_read`. A `--worktree`-only lane without a
  `ship-parallel.jsonl` entry is invisible to `ship status`/`ship list`
  even though `pmctl worktree list` would show it — reproducing exactly
  the fragmentation CC-442 exists to remove.
- Minimal schema change: none structurally required — reuse the existing 6
  fields verbatim with `run_id=""` for non-dispatch lanes (existing
  `jq -Rn --arg` construction already tolerates empty strings). An optional
  `adapter` field (empty/null when unset) would help display but is not
  required for correctness.

### a3 — Pilot walkthrough: migrate `--parallel` to the unified entry

Drafted a before/after diff (not applied — draft only) against
`scripts/lib/pmctl-ship-parallel.sh` and `scripts/lib/pmctl-ship.sh`:

- **(a)** New `pmctl_ship_run(repo_root, work_dir, ticket_id, --worktree
  [--adapter <name>] [--from <b>] [--isolation <lvl>] [--model <alias>]
  [--auto-pack|--no-auto-pack])` added to `pmctl-ship.sh`. Relocates the
  brief-writer (renamed `_pmctl_ship_brief_write`, identical body) from
  `pmctl-ship-parallel.sh`. Sequence: id-shape check
  (`_pmctl_ship_id_shape_ok`) + active-heading check
  (`_pmctl_ship_heading_exists`) → `pmctl_worktree_create` (CC-014,
  unchanged) → `mktemp` brief file (0600) → `_pmctl_ship_brief_write` →
  `pmctl_dispatch_run --lifecycle detached`. Returns via globals
  (`PMCTL_SHIP_RUN_LANE_PATH` / `PMCTL_SHIP_RUN_ID` /
  `PMCTL_SHIP_RUN_BRANCH`), matching the existing
  `DISPATCH_RECORD_STATE` global-return idiom already used elsewhere in
  this codebase — not a new shim pattern.
- **(b)** Rewritten `pmctl_ship_parallel_run` loop body calls
  `pmctl_ship_run "$repo_root" "$work_dir" "$t" --worktree --adapter
  "$adapter" ...` once per ticket instead of duplicating
  worktree-create/brief-write/dispatch-run inline.
  `_pmctl_ship_parallel_brief_write` is deleted (moved, renamed). Arg
  parsing, the duplicate/in-flight pre-flight check, the `gc.auto` trap,
  and the fail-summary all stay unchanged in the caller.

Verdict: the rewrite is clean and shim-free. Minor regression risks, all
avoidable by construction: per-lane error-message wording must stay stable
if asserted by `scripts/test-pmctl-ship.sh`; collapsing 3 distinct failure
points (worktree/mktemp/dispatch) into one `return 1` must not lose
per-cause stderr granularity (draft's `pmctl_ship_run` still emits it);
`--name` arg passed identically; dispatch ordering/timing unchanged
(`--lifecycle detached` means real parallelism is unaffected downstream).

The one genuinely open seam a3 surfaced: **where does the
`ship-parallel.jsonl` tracking-append call live?** a3's draft deliberately
left it caller-side (the `--parallel` loop builds the JSON line and calls
`pmctl_ship_parallel_tracking_append` itself after `pmctl_ship_run`
returns) specifically so it could be relocated once a2's schema decision
landed, rather than pre-judging it.

## Findings

Reconciling the three angles: a1 (keep `finish` separate) and a3's draft
diff do not conflict — a3 never touches the finish path. a2's decision
(every `--worktree` lane, dispatched or not, needs a `ship-parallel.jsonl`
entry) does interact with a3's draft: a3 intentionally structured the
tracking-append as a caller-side, generalizable step, but under a2's
decision, *any* caller of `pmctl_ship_run` — not just the `--parallel`
loop — must perform that append, including a future bare
`pmctl ship <id> --worktree` CLI call site (no `--parallel`). Leaving the
append purely caller-side risks a call site forgetting it (the exact
`ship status`/`ship list` blind-spot a2 flagged). The reconciled
recommendation is therefore to pull the tracking-append **into**
`pmctl_ship_run` itself, parameterized by `reg_dir` (defaulted from
`repo_root` the same way `pmctl_ship_parallel_run` derives it today), so no
call site — `--parallel`'s loop, or a future single-lane `--worktree`
handler in `cli/pmctl` — can omit it.

One secondary gap surfaced by a1 and not covered by a3's draft: a1's
mitigation for the bare `pmctl ship <id>` vs `pmctl ship <id> --worktree`
routing asymmetry (retaining `pmctl ship prepare <id>` as an explicit,
still-working alias so bare `pmctl ship <id>` is pure sugar for prepare, and
`_pmctl_ship_id_shape_ok` continues to discriminate a ticket-id-shaped
token from reserved words like `status`/`list`/`--parallel`) was never
exercised in a3's draft, which only touched the `--worktree`/`--adapter`
path. This is a real but small implementation detail, not a spike gap — see
Open risks.

## Recommendation

**Adopt** all three decisions:

1. **Finish call-shape**: keep `pmctl ship finish <id>` as a separate,
   unchanged verb (Option A). Do not converge it into the unified entry
   point. `--worktree`/`--adapter` never travel to `finish`.
2. **Tracking schema**: every `--worktree` lane, dispatched (`--adapter`)
   or not, gets a `ship-parallel.jsonl` entry with `run_id=""` for
   non-dispatch lanes. No structural schema change beyond that (an
   optional `adapter` display field is a nice-to-have, not required). The
   tracking-append call moves inside `pmctl_ship_run` (parameterized by
   `reg_dir`) rather than staying caller-only, so no call site can forget
   it.
3. **Pilot walkthrough**: adopt a3's draft shape —
   `pmctl_ship_run` in `scripts/lib/pmctl-ship.sh` absorbing the relocated
   brief-writer and the worktree-create/dispatch-run sequence, with
   `pmctl_ship_parallel_run` rewritten to call it once per ticket, amended
   per (2) to own the tracking-append internally.

This is enough to backfill a confident implementation ticket without
breaking the CC-439 `/ship` single-ticket contract (untouched — `/ship`
never calls `finish` or the new `pmctl_ship_run`) or reinventing CC-014's
`pmctl worktree create` (called unchanged, still the sole worktree-creation
primitive).

## Open risks

- **Bare-`pmctl ship <id>` routing asymmetry** (a1): retaining
  `pmctl ship prepare <id>` as an explicit alias so bare
  `pmctl ship <id>` (no flags) stays pure sugar for prepare, and
  `_pmctl_ship_id_shape_ok` keeps discriminating ticket-id-shaped tokens
  from reserved words (`prepare`/`finish`/`status`/`list`/`--parallel`),
  was not exercised in a3's pilot diff — it only drafted the
  `--worktree`/`--adapter` path. Small, contained routing change, but
  should be included explicitly in the implementation ticket's scope, not
  assumed.
- **Cross-path in-flight interaction** (a2): once worktree-only lanes
  share the `ship-parallel.jsonl` schema, the existing in-flight-refusal
  check in `pmctl_ship_parallel_run` (status `dispatched`/`running` blocks
  re-dispatch of the same ticket) will also block a later
  `pmctl ship <ticket> --parallel` call for a ticket that already has an
  open, un-finished manual `--worktree` lane (status `"running"`
  pre-marker). Probably correct (don't double-lane one ticket) but is a
  new cross-path interaction that doesn't exist today and should be
  exercised with a real test, not assumed correct by inspection.
- **`pmctl_ship_run`'s internal tracking-append needs `reg_dir`
  threading**: today `reg_dir` is derived once inside
  `pmctl_ship_parallel_run`; moving the append inside `pmctl_ship_run`
  means that derivation (or an equivalent default) needs to be available
  to every caller, including a future single-lane CLI handler. Not
  resolved in detail here — first task for the implementation ticket.
- The pilot diff in a3 is a draft, not applied code — actual behavior
  (error-message wording preserved, `scripts/test-pmctl-ship.sh` still
  green) must be verified once implemented, not assumed from the diff
  alone.
