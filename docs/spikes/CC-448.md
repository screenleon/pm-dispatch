# CC-448 — opencode host support：階段 1 probe（spike result）

**Status**: stage 1 (probe) complete; stage 2/3 (manifest/wiring) not started
**Date**: 2026-07-06
**Ticket**: BACKLOG.md CC-448

## Investigation scope

[[CC-448]] 三階段鏡像 [[CC-381]]→[[CC-436]]/[[CC-437]]/[[CC-438]] 的推進模式，本文件只覆蓋階段 1：
opencode 的 hook/plugin 機制實測——有無 `PreToolUse` 等價事件？payload 表達力（command？file
path？）？fail-closed 可行否？方法與 [[CC-436]] 相同：throwaway 專案目錄 + 真實帳號憑證（GitHub
Copilot/OpenAI/Mistral 已配置），用 `opencode run --format json` 觸發一個 command 動作與一個
file-write 動作，觀察 payload 與阻擋行為。

**與 CC-436 的關鍵方法差異**：codex 的 guard 落點要透過 `$CODEX_HOME/hooks.json` 這個外掛式 hook
機制；opencode 有一個**內建的宣告式 permission 設定**（`opencode.json` 的 `permission.{bash,edit,
webfetch,...}: "ask"|"allow"|"deny"`），不需要寫任何腳本或外掛就能做 command/file 層級的靜態
allow/deny。這是本次 probe 最大的意外發現，直接改變了兩個 host 的 guard binding 難度對比。

## Findings

**1. opencode 有兩套獨立的擴充機制，guard binding 應該優先用宣告式 config，不是 JS plugin。**

- **宣告式 permission config**（`opencode.json` 或 agent-level config）：`permission.bash`/
  `permission.edit`/`permission.webfetch` 可設 `"ask"|"allow"|"deny"`，`bash` 還支援
  per-pattern 物件（`{"<pattern>": "ask"|"allow"|"deny"}`）。**這是第一候選**——設定即生效，不需要
  額外進程/腳本，比 codex 的 hooks.json + 外部 script 簡單得多。
- **JS plugin hook 系統**（`@opencode-ai/plugin` package，`Plugin = (input, options) =>
  Promise<Hooks>`）：`Hooks["permission.ask"]`（input: `Permission` 物件，output:
  `{status: "ask"|"deny"|"allow"}`）與 `Hooks["tool.execute.before"]`（input:
  `{tool, sessionID, callID}`，output: `{args}`，可修改參數）提供動態、可程式化的判斷邏輯，但要求
  作者寫一個 npm module 或本地 plugin 檔案並在 config 註冊。**本次 probe 只做了型別層級的靜態分析
  （TypeScript `.d.ts`），未實測——留給需要動態邏輯（例如依賴 [[CC-346]] blast-radius 資訊）的後續
  票再驗證。**
- 對照 [[CC-436]] 的建議：宣告式 config 走「command-level guard binding 優先」路線最省事；plugin
  hook 系統則是需要更細緻邏輯時的加值選項，兩者不互斥。

**2. `permission.bash: "deny"` 實測 fail-closed，且比 codex 乾淨——模型根本不會嘗試呼叫該工具。**
`opencode run` 收到 deny 設定後，模型直接回覆「I can't run shell commands in this interface」，
沒有產生任何 `tool_use` 事件、沒有被拒絕的噪音記錄。這比 codex 的「hook 攔截並回傳錯誤訊息給模型」
更乾淨（bash 工具本身在該 session 就沒有被暴露），但也代表**沒有機會在 payload 層面攔截並記錄實際
嘗試的 command**——如果 host manifest 設計需要「記錄被擋下的具體 command 供稽核」，宣告式 config
本身做不到，需要疊加 plugin hook（`tool.execute.before`）才能拿到嘗試的 args。

**3. `permission.edit: "deny"` 單獨設定會被 bash 繞過——這是關鍵安全性發現，直接對應 CC-436 的
file/command 不對稱疑慮。**
設定 `edit: "deny"` + `bash: "allow"` 時，模型改用 `printf 'hello\n' > probe.txt`（bash 工具）
寫檔案，繞過 `edit` 權限，**probe.txt 確實被建立**。`edit` 與 `bash` 是兩個獨立的權限閘門，管的是
不同工具介面，不會互相連動——跟 codex 的「透過 shell 重導向寫檔案只會走 Bash 動作，天生繞過
file-level guard」是同一類問題（見 [[feedback_cut_capability_close_all_paths]]）。**結論：任何
opencode-host 的 file-level guard binding，若只設 `edit: deny` 而不同時管控 `bash`，形同虛設。**

**4. `edit: "deny"` + `bash: "deny"` 同時設定時，`opencode run` 會掛起（timeout 無回應），即使帶
`--dangerously-skip-permissions`。**
這與單獨 `bash: "deny"`（乾淨回覆不能執行）行為不一致，本次 probe 在 90 秒 timeout 內未見任何輸出
即被中止；fail-closed 語意成立（probe.txt 確認未被建立），但不是預期中「乾淨拒絕」的形式，而是無聲
掛起——如果 host manifest 真的採用「全部工具都 deny」當保守預設，需要先解開這個掛起原因，否則
headless dispatch 路徑會卡死（同類問題見 CC-436 的 `--dangerously-bypass-hook-trust` 掛起發現）。

**5. Bash 工具呼叫 payload 比 codex 更豐富。**
透過 `--format json` 追蹤看到的 `tool_use` 事件 `input` 欄位：
```json
{"command": "echo allowed-control-group", "timeout": 120000,
 "workdir": "/tmp/cc448-opencode-repo", "description": "Echoes the allowed control group"}
```
`command` + `workdir` 直接映射 `pmctl guard check --command <cmd>`（在 `workdir` 下執行），
額外還有 `timeout`/`description` 欄位可供稽核記錄用，比 codex Bash payload（只有 `command` +
`cwd`）多一點資訊，但欄位映射結論相同：command 動作欄位齊全可直接用。

## Recommendation

**Adopt，且 opencode 的 command-level guard binding 比 codex 更容易落地（宣告式 config，無需外部
腳本），但 file-level guard 兩邊都有同一個結構性弱點：edit/write 權限與 bash 權限是分離閘門，必須
兩者都納管才算真正擋住檔案寫入。**

1. [[CC-438]]（host manifest schema）定案前必須把「opencode 用宣告式 permission config、codex 用
   hooks.json + script」這兩種**形態不同**的 guard binding 表達方式都納入考慮，schema 不能假設
   guard binding 一定是「產生一個腳本檔案」——opencode 這邊更接近「產生一段 config 片段」。
2. **file-level guard 的『閉合所有路徑』原則要寫進 schema 驗收條件**：任何 host 的 file guard
   binding，若只管控 edit/write 專屬工具卻放行 bash/shell，視為未完成、不能宣告「file guard
   已支援」。這對 codex（`apply_patch` vs `Bash`）與 opencode（`edit` vs `bash`）是同一類問題。
3. `edit: deny` + `bash: deny` 同時設定的掛起原因是階段 2（manifest）落地前必須解開的 blocking
   open risk，不能繞過。
4. 沿用 CC-436 的立場：native guard 是防禦縱深，`write_guard_mode: cli-only` 繼續當 fallback。

## Open risks

- `edit`+`bash` 同時 deny 的掛起原因未查明（是等待某個永遠不會到來的互動提示？還是 opencode 內部
  重試迴圈？）——阻擋階段 2 manifest 設計對「保守預設全 deny」的假設。
- JS plugin hook 系統（`permission.ask`/`tool.execute.before`）完全未實測，只有型別層級的靜態分析；
  若階段 2 manifest 需要比宣告式 config 更細的邏輯（例如依 command pattern 動態決策而非整個
  `bash` 工具二元 allow/deny），需要額外一輪 probe 驗證 plugin 真的能被 headless `opencode run`
  載入並生效。
- `webfetch`/`doom_loop`/`external_directory` 三個額外 permission 欄位完全未測試，範圍外。
- 本次只測了 `openai/gpt-5.4-mini-fast` 一個 model；不同 model 對「工具被 deny 時的反應方式」
  （直接回覆 vs 嘗試呼叫後被拒）可能不同，會影響「模型完全不嘗試」這個乾淨行為是否可靠。
