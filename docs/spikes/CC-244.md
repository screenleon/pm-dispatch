# CC-244 — Typed artifact pipeline: spike → brief → handover schema (spike result)

**Status**: complete
**Date**: 2026-08-23
**Ticket**: BACKLOG.md CC-244

## Investigation scope

1. Retrofit-fit — do the 28 existing `docs/spikes/*.md` files map cleanly onto
   the design sketch's `scope`/`findings`/`constraints`/`decisions`/`phase3_handover`
   schema, or does real spike content resist that shape?
2. Courier-cost claim — is the main-thread token/re-read cost from prose
   spikes actually measurable, or was premise (b)/(c) in the ticket's
   Problem statement assumption rather than measurement?
3. Frontmatter vs. sidecar — should structured fields live as spike-file
   YAML frontmatter (per the sketch) or a separate sidecar, and what
   actually reads `decisions_resolved=true` to avoid re-asking resolved
   questions?
4. Validator/tooling scope — is a dedicated `spike-validate.sh` +
   `gen-brief-from-spike.sh` pair justified now, or does existing lint
   tooling already cover the leverage without new scripts?

## Angles

### a1 — Retrofit-fit + frontmatter-vs-sidecar shape

Sampled 6+ of the 28 `docs/spikes/*.md` files (CC-060, CC-249,
cc209-codegraph-phase1, the CC-229-substrate-{scope,claude,codex,synthesis}
group, CC-445-448-cross-host-live-acceptance, CC-408-next-step-router).

0/6+ sampled files cleanly map onto the sketch's five-part shape. The two
closest partial fits (CC-249, CC-408) align only because they already follow
`docs/spikes/README.md`'s pre-existing six-part skeleton (Investigation
scope / Angles / Findings / Recommendation / Open risks / Next tasks) — a
different, already-in-de-facto-use convention, not the sketch's shape.
Phased/multi-file spikes (CC-060, CC-209, the CC-229 group, CC-445-448)
actively resist the sketch: they use custom per-investigation structures
(numbered phases, lettered A–F sections, executable runbook sections) the
five-part shape can't accommodate. `constraints` and `phase3_handover` as
named headings appear in **none** of the 28 files.

`dispatch_handover_v1` — the sketch's stated "mirror target" — is itself
neither pure frontmatter nor a sidecar: it's a fenced code block with a
metadata header, embedded in agent response text, extracted to an ephemeral
`/tmp` file at consumption time. The closer real precedent for "structured
header on a persisted artifact, referenced by pointer" is
`pm-prep-snapshot.sh`'s output — a separate `---`-delimited file referenced
via a `snapshot_file:` field with explicit path-safety ingestion rules in
`agents/project-pm.md` § Snapshot ingestion. None of the 28 committed spike
docs has YAML frontmatter today.

`decisions_resolved` has zero hits anywhere in the repo outside the CC-244
ticket text — no producer, no reader. The working analog
(`pm-prep-snapshot.sh` → `snapshot_file:` → `agents/project-pm.md`'s
Snapshot ingestion section) shows what a functioning producer/consumer pair
looks like; `decisions_resolved` has no equivalent triple. A consumer would
need to sit at brief-authoring time (e.g. a new "Spike ingestion" section in
`agents/project-pm.md`, or `gen-brief-from-spike.sh`) — neither exists.

### a2 — Courier-cost claim validity

Ticket premises (b) "loses invariant checkpoints... re-ask resolved
questions" and (c) "main thread inlines the whole spike when courier-ing"
are not observed anywhere in the current pipeline — they are unverified
assumptions, not measured problems. Lazy-read discipline already exists and
predates CC-244: `agents/spike.md`, `commands/spike.md`,
`agents/project-pm.md:198`, and `docs/dispatch-brief.md:76` all mandate
`grep -n`/`sed -n` section-targeted reads over `docs/spikes/*.md`, never
full-file Read. No script anywhere in the repo consumes a finished spike
file at all yet (grep for `cat`/Read over `docs/spikes/*.md` in `.sh` files
returns nothing) — there is no re-read path to measure a cost against. The
only "inlining" that happens is of pre-synthesis raw angle findings during a
spike's own creation, which is unavoidable Agent-tool-call output
independent of any schema.

Measured 3 representative files (CC-448.md 7.9KB, CC-436.md 7.4KB,
cc209-codegraph-phase1.md 15KB): under the already-mandated grep/sed
convention, a consumer reads ~30–35% of file bytes (header + Recommendation
section), not 100%. A hypothetical frontmatter-only read would shave that
further, but the marginal gain over the existing convention on files this
small is modest. No incident/git-log evidence was found (searched
BACKLOG.md, BACKLOG-ARCHIVE.md, CHANGELOG.md, DECISIONS.md) of an agent
re-litigating a resolved spike decision.

### a3 — Validator/tooling scope precedent

`handover-validate.sh`'s real complexity (398 lines) is justified by it
being a security-critical shell-injection sanitization gate (values are
`printf %q`'d into subprocess dispatch commands) plus cross-referencing 3
live policy-enum YAML files and filesystem existence checks — fundamentally
different in kind from a frontmatter lint, because its output is spliced
into a subprocess launcher. A `spike_v1` frontmatter block has no equivalent
security surface (read by an LLM synthesizing a brief, not interpolated
into a shell command) — the justification that carries
`handover-validate.sh`'s complexity does not transfer to a spike validator.

`tools/lint/lint-frontmatter.sh` already exists and is CI-wired
(`.github/workflows/lint.yml`), but scoped only to `agents/*.md`,
`commands/*.md`, `skills/*/SKILL.md`, and validates YAML syntax only (no
field presence/enum/cross-field checks) — and none of the 28 spike docs
currently have YAML frontmatter to lint (all start with `# Title` then
bold-prose metadata lines, not a `---` fence).

`gen-brief-from-spike.sh`'s proposed job (mechanical extraction) is
premature by construction: there's no `spike_v1`-shaped corpus yet (0/28
use frontmatter), and today's spike→brief handoff is explicitly
PM-mediated per `commands/spike.md`'s own stated output contract ("open or
plan the follow-up ticket with `/pm`") — mechanizing extraction needs real
`spike_v1` instances to exist first.

## Findings

- **Retrofit-fit: fails.** 0/6+ sampled spike docs map onto the sketch's
  five-part shape; phased spikes actively resist it. The shape that *is*
  already in de-facto use across all 28 files is `docs/spikes/README.md`'s
  own six-part skeleton — a convention that already exists and needs no new
  schema to be adopted, because it already is.
- **Courier-cost claim: unverified.** No measured re-read cost, no
  consumption script exists to measure against, no incident of re-asked
  resolved questions found. Lazy-read discipline (grep/sed section-targeted
  reads) already mitigates the theoretical cost and predates this ticket.
- **`decisions_resolved`: producer without a consumer.** Adopting the field
  alone accomplishes nothing; a real fix requires building a consumer
  (spike-ingestion step in `agents/project-pm.md` or in
  `gen-brief-from-spike.sh`) that does not exist and was not itself
  investigated by this spike.
- **Frontmatter vs. sidecar: if ever adopted, sidecar fits repo precedent
  better.** The closer real analog (`pm-prep-snapshot.sh` →
  `snapshot_file:` pointer) is a sidecar-by-pointer, not embedded
  frontmatter — and that pattern could be introduced additively for new
  spikes only, without retrofitting the 28 existing files.
- **Validator/tooling: premature.** `handover-validate.sh`'s complexity is
  justified by a shell-injection security surface that a spike frontmatter
  block does not share. `lint-frontmatter.sh` already gives free YAML-syntax
  CI coverage and could be extended to `docs/spikes/*.md` at near-zero cost
  *once* frontmatter exists — but none does yet.

## Recommendation

**Reject** `spike_v1` as specified in the design sketch (frontmatter +
`scope`/`findings`/`constraints`/`decisions`/`phase3_handover` sections,
mirroring `dispatch_handover_v1`).

Rationale: all three investigation angles converge on the same conclusion.
The motivating courier-cost premise is unverified against the actual
pipeline (a2), which already has lazy-read discipline predating this
ticket. The proposed schema shape does not fit real spike content — 0/6+
sampled docs mapped onto it (a1; the full 28-file population was not
exhaustively checked against the shape), and the shape that *does* already work
(`docs/spikes/README.md`'s six-part skeleton) is a different, already-adopted
convention (a1). Building `spike-validate.sh` and `gen-brief-from-spike.sh`
now is premature: no `spike_v1`-shaped corpus exists to validate or extract
from, and the validator complexity precedent (`handover-validate.sh`) does
not transfer because a spike frontmatter block has no shell-injection
surface (a3).

No implementation ticket is justified. The existing `docs/spikes/README.md`
six-part skeleton remains the spike-doc convention; no schema change, no new
scripts.

If a courier-cost problem is later *measured* (not assumed) — e.g. a
concrete incident of an agent re-reading a full spike file, or re-asking a
resolved decision, with evidence — the lighter next step per this spike's
findings is: (1) a small sidecar-by-pointer (mirroring
`pm-prep-snapshot.sh` → `snapshot_file:`) added additively to *new* spikes
only, not frontmatter retrofitted onto 28 existing files; (2) extend
`tools/lint/lint-frontmatter.sh`'s scan-directory list to
`docs/spikes/*.md` for free CI coverage once such sidecars exist; (3) revisit
`gen-brief-from-spike.sh` only after several real instances accumulate and a
PM has manually extracted briefs from them a couple of times — mirroring
the same "3+ instances repeating" trigger discipline this ticket itself used
to promote from someday.

## Open risks

- The `decisions_resolved` re-ask-prevention mechanism was never designed
  even hypothetically — if a real courier-cost incident surfaces later, the
  consumer side (where and when the field gets read) still needs original
  design work, not just field-list bookkeeping.
- This spike sampled a subset (6+/28) of spike docs for the retrofit-fit
  check, not all 28; the "resists the shape" finding for phased spikes is
  strong (structural, not close-call), but the exact fit ratio across all 28
  was not exhaustively tabulated.
- No mechanism currently prevents someone from writing a new spike doc that
  drifts from the README six-part skeleton; that drift-prevention gap is
  outside this ticket's scope but is the more concrete leverage point than
  `spike_v1` would have been.

## Next tasks

None. No follow-up implementation ticket is opened. CC-244 closes on this
reject verdict; re-open only if a concrete courier-cost incident is
measured (see Recommendation).
