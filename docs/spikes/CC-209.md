## 1. Problem & investigation scope

Codex briefs rely on a manually-specified `files:` block for context (see
`docs/dispatch-brief.md`). If the list is incomplete, Codex spends tokens
exploring the target repo with grep/read. CC-209 asks whether a pre-built code
index can auto-supply the relevant files and cut per-brief token cost.

Scope (from the CC-209 ticket): (1) understand the install model, (2) identify
the query API, (3) prototype a `--codegraph-enrich` path, (4) measure token
delta on 3 briefs. Per owner decision 2026-05-21 this spike is **investigation
only** — items 3–4 move to CC-222.

## 2. Candidates

| | **colbymchenry/codegraph** (primary) | **nashsu/llm_wiki** (reference only) |
|---|---|---|
| Form | CLI + MCP server, 100% local, MIT, ~9.5k★ | Tauri desktop app, local HTTP API `:19828` |
| Index tech | tree-sitter AST → SQLite (FTS5 keyword search); **no LLM** | **LLM two-step chain-of-thought ingest** |
| Index speed | 91 files in 2.9 s (measured, §3.2) | slow, token-costly; SHA256-skips unchanged files |
| Output | `path:line` symbols + entry points + optional snippets | hybrid keyword + optional vector + graph expansion |
| Fit for CC-209 | direct — `context` output maps to the `files:` block | poor — LLM-built index is the opposite of lightweight |

`llm_wiki` is a **reference point only**: it demonstrates the "persistent index
instead of re-RAG each query" idea, but its LLM-based ingest is token-costly and
its code-structure indexing is far weaker than codegraph's AST-native graph. Not
a candidate.

## 3. Track A — hands-on integration findings

### 3.1 Install model & integration surface

codegraph ships as a **CLI** and an **MCP server**. pm-dispatch is shell-based
and dispatches *file-backed* briefs; it is not itself an MCP client. Two shapes:

- **CLI preflight — recommended [lightweight].** At brief-authoring time, run
  `codegraph context "<goal>" --no-code` against the *target* repo and paste the
  resulting `path:line` list into the brief `files:` block. codegraph stays
  entirely outside `codex-dispatch.sh` and outside the security-sensitive
  dispatch path.
- **MCP tool — rejected [heavier].** Register codegraph's MCP server with the
  *executing* Codex so it queries the graph live. Adds an MCP dependency to
  every dispatch; the extra win (live call-graph traversal) is beyond CC-209's
  goal of pre-supplying file context.

**Who runs codegraph — the dispatched executor does not.** In the recommended
CLI-preflight model the executor (Codex, launched by `codex-dispatch.sh` under a
`workspace-write` sandbox) never invokes codegraph. codegraph runs *before*
dispatch, on the main thread, outside the sandbox; the brief that reaches the
executor already carries an enriched `files:` block. The executor is sped up
because it receives a better file list — not because it queries codegraph
itself. This keeps the dispatch path's trust surface unchanged: no codegraph
binary required on the executor's PATH, no MCP registration in Codex config, no
extra sandbox permissions.

**Model B — executor calls codegraph live (considered, not recommended).**
Having the dispatched Codex run `codegraph query` / `context` itself, or use the
codegraph MCP server during execution, is technically possible but heavier:

- The target repo must already be indexed before dispatch (`.codegraph/` present).
- codegraph must be on the executor's PATH, or its MCP server registered in
  Codex config (`codegraph install` can do this).
- `codegraph query` is read-only against the local SQLite DB inside the repo, so
  it would plausibly run under the `workspace-write` sandbox — but this is
  unverified and would need a smoke test before relying on it.
- It partly defeats the goal: the executor would then spend its own tokens
  deciding when to query and parsing results, trading exploration cost for
  query-orchestration cost.

Preflight keeps that decision cost on the main thread (at brief-authoring time)
and leaves the executor a pure consumer. Model B is recorded for completeness; a
middle-ground hybrid (preflight enrichment plus an optional "you may run
`codegraph query`" note in the brief) is possible but adds a complexity tier and
is **not** part of the CC-222 scope.

### 3.2 Measured numbers (hands-on, this spike)

Test repo: `japanese-site` (Go + TypeScript + Python; 91 source files).

| Metric | Value |
|---|---|
| Full index (`codegraph index`) | **2.9 s** — 1,152 nodes, 2,237 edges, 2.68 MB SQLite |
| `context` query latency (warm index) | ~0.4 s |
| `context --no-code` output | **~517 chars (~130 tokens)** — `path:line` symbols + entry points |
| `context` with code snippets | ~2 KB |
| `context -f json` | ~8.8 KB |

The index covers only code-language files: of the full repo (206 jsonl + 198
json + 46 md + 11 sh + …) only the 91 Go/TS/Py files were indexed. The
`--no-code` form is the brief-enrichment primitive — ~130 tokens injected to
potentially avoid many exploration reads.

### 3.3 Query → `files:` mapping

The `--no-code` markdown is already in `files:`-block shape. Real output for
"add a kanji corpus endpoint filtered by JLPT level" surfaced
`server/internal/content/jlpt/parse.go`, `corpus/load.go`, `overlay.go`,
`web/src/api.ts`, `apiTypes.ts`, `staticApi.ts` — i.e. exactly the files a
hand-written brief would list.

### 3.4 Limitation — lexical overlap (the `fast`-tier ceiling)

The `fast` tier search is FTS5 keyword matching: the query string must
lexically overlap real symbol names.

- "fix SRS scheduling interval calculation" → **empty** Related Symbols.
- "review schedule srs answer grading" → hits `grade.go`, `grade_test.go`,
  `handlers.go:quizAnswer`.

**Implication**: enrichment must be **additive** — it augments, never replaces,
the human-written `files:` list. A whiffed query must degrade to current
behavior, not to an empty list.

### 3.5 Shell coverage — pm-dispatch self-indexing

The owner asked whether pm-dispatch itself could also be covered (managing
target repos is the primary goal; self-coverage would be a bonus). **codegraph
cannot do it.** codegraph's language set is TS/JS/Py/Go/Rust/Java/C#/PHP/Ruby/
C/C++/Swift/Kotlin/Dart/Svelte/Vue/Liquid/Pascal/Scala — no shell. Probe:
`codegraph index` on pm-dispatch (53 `.sh` files) → "No files found to index".
`tree-sitter-bash.wasm` *is* bundled (inside the `tree-sitter-wasms` dependency,
which ships every grammar) but codegraph registers no bash language module and
no extraction queries — grep for any bash reference in codegraph's `dist/`
returns nothing. Adding `**/*.sh` to the config `include` glob would not help.

pm-dispatch self-coverage would require an upstream codegraph bash module or a
separate ctags-based index (see §4 Q3). Since target-repo management is the
primary goal, this is a **known limitation**, not a blocker.

## 4. Track B — independent index-strategy review (Codex)

A Codex dispatch ran an independent second opinion on index strategy and lighter
alternatives (raw report: [`CC-209-track-b-codex.md`](CC-209-track-b-codex.md)).
Summary:

- **Q1 tier** — `fast` tier sufficient [lightweight]; LSP/embedding rich tiers
  [heavy], justified only for high-precision resolution beyond CC-209's goal — rejected.
- **Q2 cadence** — (a) index per-dispatch [medium], (b) persistent per-repo
  index + `sync`-on-use [lightweight, recommended], (c) watcher daemon [heavy].
  Degrade: sync failure / no index → on-demand full index + warning.
- **Q3 lighter alternatives** — universal-ctags [lightweight], git grep /
  ripgrep [lightweight], codegraph `query`/`files` subcommands [lightweight] —
  all cheaper but lack task→symbol semantic ranking; ctags/rg are good at
  explicit symbol discovery, weaker on vague natural-language goals.
- **Q4 risks** — stale index [high], missing/empty index [high], multi-repo
  index management [high], extra npm dependency [medium], `.codegraph/` artifact
  hygiene [medium].
- **Verdict** — adopt an optional codegraph `fast`-tier path with `sync`-on-use
  (not a resident daemon) and graceful fallback to existing `files:` behavior;
  smallest change that targets the real pain point without heavy services.

Tracks A and B converged independently: **`fast` tier, optional, additive,
`sync`-on-use, degrade-safe.** No disagreement between the two tracks.

## 5. The LSP / RAG question — resolved

The owner saw codegraph docs mention LSP and RAG/embeddings and was unsure
whether to use them.

- codegraph is **tiered**. The default `fast` tier is pure tree-sitter —
  **no LSP, no embeddings**. This is the recommended tier.
- LSP resolution + vector embeddings (HNSW) are *opt-in richer tiers* →
  classified [heavy] → **rejected** under the lightweight-first constraint.
- The cost of the `fast` tier is the §3.4 lexical-overlap miss. The
  lightweight-first preference means accepting that miss (mitigated by additive
  enrichment) rather than importing heavy semantic-search machinery.
- "Speeding up indexing" is largely a non-issue: the `fast` tier already indexes
  91 files in 2.9 s. The slow path *is* the heavy tier being rejected — so the
  lightweight choice and the fast-index choice are the same choice.

## 6. Recommendation

1. **Adopt** codegraph `fast` tier — optional, opt-in, for code-language target repos.
2. Integration shape: **CLI preflight** (§3.1) — codegraph stays out of `codex-dispatch.sh`.
3. Enrichment is **additive** — appends to the human `files:` list, never
   replaces it; a whiffed or empty query is a no-op.
4. Cadence: **persistent per-repo index + `sync`-on-use** (Track B option b).
   Bootstrap `codegraph index` once per target repo; `codegraph sync` before
   reuse; on missing or stale index, full index + warning.
5. Tier: **`fast` only**. LSP/embedding tiers rejected.
6. pm-dispatch self-coverage: **out of scope** — shell unsupported (§3.5),
   recorded as a known limitation.
