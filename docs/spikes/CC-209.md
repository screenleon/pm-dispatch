## Findings

### Memori — what it is

Python SDK (TS variant exists). Post-hoc memory extraction. Conversations +
tool calls → LLM "augmentation" extracts facts + entities + semantic triples
(subject-predicate-object) → stored in pluggable DB (PostgreSQL / MongoDB /
CockroachDB via SQLAlchemy/dbapi) or Memori Cloud → retrieved via embedding
+ relevance threshold. LLM/framework-agnostic (OpenAI / Anthropic / Bedrock
/ Gemini / xAI; LangChain / Pydantic AI / Agno). 14.8k stars; 81.95% accuracy
on LoCoMo benchmark using 4.97% tokens vs full-context.

| Axis | Memori |
|---|---|
| Data model | Entity → Facts + Semantic Triples; Process + Session; Conversation → Augmentation |
| Storage | Pluggable SQL/NoSQL backends; cloud + local hybrid |
| Distillation | Per-turn `capture_turn()` LLM augmentation; optional `compaction()` |
| Retrieval | Embedding + relevance threshold (configurable) |
| Lifecycle | No explicit TTL; manual eviction |
| Portability | **High** — LLM-agnostic, framework-agnostic by design |
| Claude coupling | None |
| License | Unconfirmed (Uncertainty — needs verify before any code-text citation) |

### agentmemory — what it is

TypeScript/Node (≥20) on iii engine. Persistent memory for **Claude-native
agents** (Claude Code, Cursor, Cline) via 12 lifecycle hooks. Four-tier memory
pyramid: working (raw) → episodic (session summaries) → semantic (facts) →
procedural (workflows). Storage: SQLite + in-memory BM25/vector index (no
external DB). Retrieval: BM25 + vector + knowledge-graph traversal fused via
Reciprocal Rank Fusion (RRF). Apache-2.0. 16.7k stars; 95.2% recall@5 on
LongMemEval-S. Inter-agent coordination primitives (Signal/Sentinel/Checkpoint).

| Axis | agentmemory |
|---|---|
| Data model | Raw → Compressed → Memory (type: pattern/preference/architecture/bug/workflow/fact); GraphNode × GraphEdge (file/function/concept) |
| Storage | SQLite + in-memory BM25/vector index; persist to disk; no external DB |
| Distillation | 12 lifecycle hooks auto-feed → dedup → privacy filter → LLM compression → index |
| Retrieval | RRF fusion: BM25 + vector + knowledge-graph |
| Lifecycle | Ebbinghaus decay, configurable TTL, manual eviction |
| Portability | **Low** — 12 Claude-specific hooks; iii engine + Claude Agent SDK deep coupling |
| Claude coupling | High |
| License | Apache-2.0 |

## Pilot walkthrough

Per `[[feedback_spike_pilot_required]]` (added 2026-05-24 after CC-249 retro):
every API-design spike MUST include a pilot walkthrough.

This spike's pilot is necessarily **hypothetical** — the CC-211 / CC-232 /
CC-237 frameworks don't exist yet, so we can't actually wire an end-to-end
flow. What the pilot DOES demonstrate is that **at least one identified
pattern survives the CLI-agnostic boundary** when projected onto pm-dispatch's
v0.3.0 architecture.

### Pilot subject

Project agentmemory's `Memory` shape (the data-layer record, NOT the capture
hooks) onto a hypothetical `core/schema/memory.schema.json` accessed via
`pmctl memory get <id>`.

### Sketch

```jsonl
// Stored at: ~/.pm/state/memory/<id>.jsonl  (CLI-agnostic location)
{"id":"feedback_codex_routing","tier":"semantic","scope":"feedback","triples":[{"s":"work-dispatch","p":"requires","o":"Q1Q2Q3-decision-tree"}],"body_md":"<verbatim current card content>","provenance":{"origin_session":"a0bd...","first_recorded":"2026-05-13"},"lifecycle":{"ttl":null,"decay":"none","supersedes":null}}
```

- `tier`: agentmemory's 4-tier (semantic for hand-authored feedback cards;
  working for raw episodes; episodic for distilled session summaries;
  procedural for workflow templates)
- `triples`: Memori-inspired triples for queryability
- `body_md`: preserves existing card content verbatim (zero-loss migration)
- Location: `~/.pm/state/memory/` (NOT `~/.claude/projects/.../memory/`)
- Access: `pmctl memory get feedback_codex_routing`, `pmctl memory search 'routing'`
- Adapter calls: Claude Code's UserPromptSubmit hook calls
  `pmctl memory list-index` → formats output → injects. Future Codex adapter
  does the same against the same pmctl interface.

### Pilot verifies

1. **Schema can absorb existing pm-dispatch card content** without loss
2. **Storage location is CLI-agnostic** (not under any CLI's config dir)
3. **Access API is via pmctl** (no direct file reads from CLI hooks)
4. **The shape combines patterns from both candidates** (agentmemory tier +
   Memori triples) without forcing a choice between them
5. **Future CLI adapters reach the same data** through the same pmctl interface

### Pilot does NOT verify

- That CC-211 / CC-232 / CC-237 will actually adopt this shape (framework
  not built yet)
- That triples are best hand-authored vs LLM-extracted
- That the 4-tier classification is the right boundary set
- Storage backend choice (jsonl vs SQLite vs both)
- Retrieval algorithm (RRF / embedding / keyword / hybrid)
- Any performance/scale property

### Pilot conclusion

At least one absorption pattern survives the portability boundary cleanly
(agentmemory's `Memory` shape, ported to a `pmctl`-accessible location with
Memori's triples bolted on). This validates the **direction** for future
impl PMs — they have a workable starting point when their framework
crystallizes. The pilot is **NOT a commitment** to this exact shape.
