# CC-476 — opencode `edit`+`bash` 同時 deny 掛起根因調查 (spike result)

**Status**: complete
**Date**: 2026-07-09
**Ticket**: BACKLOG.md CC-476

## Investigation scope

CC-448 階段 1 probe 發現 opencode 宣告式 permission config 若同時設
`edit: deny` + `bash: deny`，`opencode run` 會無聲掛起（90 秒 timeout 內無輸出即被
中止），即使帶 `--dangerously-skip-permissions`；單獨 `bash: deny` 則乾淨拒絕。
本 spike 要回答：掛起的觸發條件與根本機制是什麼，並在三個選項中給出建議——
(a) 掛起有解，記錄解法；(b) 掛起無解但有繞過方式；(c) 掛起無解也無繞過，CC-448
階段 2 manifest 需改設計。

## Angles

### a1 — 重現掛起、檢視 process 狀態
用 CC-448 probe 原本的 `openai/gpt-5.4-mini-fast` model，10 次試驗
`edit:deny`+`bash:deny`（bare string），含/不含 `--dangerously-skip-permissions`，
新鮮/git-初始化目錄——**全數 11–35s 內乾淨完成，正確 fail-closed 拒絕，無掛起**。
改用 `mistral/mistral-large-latest` 則重現出外觀相同的「無聲掛起、0 bytes、
timeout ~60–90s」症狀，但關鍵是：**同一 mistral model 在 `edit:allow`+`bash:allow`
（完全無 deny）下也掛起**；重跑同一 mistral 呼叫則改為立即回傳 401
Unauthorized。結論：至少 mistral 這個案例的掛起是 provider/auth 層的巧合，與
permission config 無關。未能在掛起當下即時 `strace`/`ps` 抓到 process 狀態
（process 檢查時已結束）——這是缺口而非正向發現。排除 stdin/TTY 等待、
deny+deny 專屬的內部 promise 死結（allow+allow 下 mistral 也掛起即反證此假設）、
版本漂移（binary 版本與 CC-448 探測時相同）。

### a2 — opencode 原始碼/issue tracker 先例調查
確認上游 repo 為 `anomalyco/opencode`（非 `sst/opencode`），套件
`opencode-ai`，本機版本 1.17.8，npm 最新 1.17.16。原始碼
`packages/opencode/src/permission/index.ts` 的 `ask` 函式顯示：`deny`
命中即同步/立即 `return` `DeniedError`——fail-fast，無論被 deny 的工具數量，
沒有「全部工具都 deny」的特殊分支。所有 tracker 中的掛起 issue 都可追溯到
`ask`（而非 `deny`）在 headless 情境下建立了一個永遠不會被 resolve 的
`Deferred`：
- #3503（已關）：`bash:"ask"` 在 `opencode run` 模式下無聲掛起。
- #14473（已關）：根因為 `tool/bash.ts` + `permission/next.ts`
  （現 `index.ts`）：`external_directory` 預設為 `"ask"`，headless 下等待的
  `Deferred` 永不 resolve。
- #22167/#13715（已關，重複票）：subagent 遇到被禁止/被 ask 的工具時整個
  session 掛起。
- **#35073（OPEN，針對本機安裝的確切版本 1.17.8 提出）**：同步 subagent
  （task 工具，`action:"run"`）被誤判為「interactive」，其權限 ask 等待一個
  永不會出現的人類回應者，無限期掛起。根因在 `session/prompt.ts` 的
  `askNonInteractive` 判斷。修復 PR #35823 開著未合併——走訪 `parentID`
  chain，回覆 reject 或 once 而非留下未 resolve 的 Deferred。
- #4129（已關，v1.0.45）：表面上像「deny 導致掛起」，但 maintainer 澄清是
  UI 可見性 bug——deny 正確中止了 agent loop，只是 TUI 沒有顯示任何指示，
  看起來像凍結；並非真正掛起。與 deny 為同步行為一致。
缺口：沒找到明確以「edit:deny + bash:deny」為觸發條件的 issue——所有掛起回報
都圍繞某處的 `ask`（顯式設定或某個未設定類別預設為 ask，如
`external_directory`）resolve 失敗。

### a3 — 縮小觸發組合（combinatorics）
Schema 有 5 個 permission key：`edit`、`bash`（bare string 或 per-pattern
object）、`webfetch`、`doom_loop`、`external_directory`。用同一 model
（`openai/gpt-5.4-mini-fast`，95s timeout）測試矩陣：
- 單一工具 deny（`bash:deny` only）→ 乾淨、可靠（baseline）。
- `edit:deny`+`bash:deny`（bare string），write+confirm prompt → **掛起 2/2**；
  fetch+write+confirm prompt → **掛起 1/1**。
- `edit:deny`+`webfetch:deny`（bash 留 allow）→ 乾淨——模型透過 bash（curl+
  redirect）繞過兩者。
- `edit:deny`+`bash:deny`+`webfetch:deny`（三者皆 bare string），
  fetch+write+confirm → 乾淨 2/2；但同組態換成 write+confirm（無 fetch）→
  **1 掛起 / 1 乾淨——相同 config+prompt 卻 flaky**。
- `edit:deny`+`bash:deny`+`doom_loop:deny`（無 webfetch）→ 掛起 1/1。
- `edit:deny`+`bash:deny`+`webfetch:allow`（顯式）→ 掛起 1/1。
- `bash:deny`+`webfetch:deny`（edit 留 allow）→ 掛起 1/1。
- `doom_loop:deny`+`external_directory:deny`（bash/edit allow）→ 乾淨——prompt
  從未動用到被 deny 的權限。
- `bash:{"*":"deny"}` object 形式 only → 乾淨（行為同單工具 bare deny）。
- `edit:deny`+`bash:{"*":"deny"}`（**object 形式**，非 bare string）→ **乾淨
  2/2**——與 row 2/3 的 bare-string `edit+bash` 明顯不同（後者可靠掛起）。
結論：既非單純「edit+bash 特定組合」，也非單純「任兩個以上同時 deny」。單一
工具 deny 永遠乾淨。移除模型會用到的每一條能力路徑的 multi-deny（bare-string
形式）會可靠或間歇性掛起（`edit+bash` 兩個 prompt 下都 3/3 掛起；
`bash+webfetch` 掛起；`edit+doom_loop` 一次掛起一次沒有）。同時 deny `edit`+
`webfetch` 但留 `bash` allow 從未掛起，因為模型會透過 bash 逃逸（這是繞過，
不是 bug 不存在）。全三者 deny 是 **flaky**（相同 config+prompt、不同目錄，
2 乾淨/2 掛起）——排除「掛起是被 deny 的 key 組合的簡單決定性函式」這個假設，
更像是 race condition。`bash` 的 bare-string 形式 vs per-pattern-object 形式
有差：`edit:deny`+`bash:"deny"` 可靠掛起（3/3），`edit:deny`+
`bash:{"*":"deny"}` 乾淨（2/2）——暗示 `bash` 為 object 形狀時走的程式碼路徑
與 string 形狀不同（與 a2 讀到的 `evaluate()` 需逐 pattern 解析一致）。
a3 提出的實務建議：偏好 `bash` 用 per-pattern object 形式（`{"*":"deny"}`）
搭配 `edit`/`webfetch` bare deny 作為「安全」保守-deny 形狀——但樣本數小
（2/2），考量到其他組合觀察到的 flakiness，需要更多試驗才能信任。

## Findings

三個角度合起來指向一個**尚未完全排除歧義、但有明確優先假設**的局面：

1. **a2 的原始碼閱讀（`deny` 同步 fail-fast，無特殊分支）與 a3 的實證重現
   （相同 bare-string `edit:deny`+`bash:deny` config 在同一 model 上
   可靠掛起 3/3）表面矛盾**，但兩者不是互斥的——a2 只讀了 `deny` 分支本身；
   若某個未被 a3 明確控制的欄位（例如未設定的權限類別預設值、或
   `evaluate()` 對 bare-string vs object 形式的路由差異）在特定條件下解析成
   `ask` 而非 `deny`，就會落入 a2 已確認會掛起的 `ask`→未解 `Deferred`
   路徑，而不是 a3 標題所暗示的「deny 本身有 bug」。
2. **a1 用同一 model、同一名義 config（edit:deny+bash:deny）跑 10 次全部
   乾淨，而 a3 用同一 model 同一名義 config 跑 3/3 可靠掛起**——這個直接
   矛盾本身就是資料：兩者的 harness、prompt 精確用字、或執行環境
   （fresh vs git-init 目錄、confirm 步驟措辭）存在未被雙方筆記完全對齊
   的差異。openai/gpt-5.4-mini-fast 這個 model 名稱也可能是別名，實際路由
   到的後端版本/延遲特性在不同時間點呼叫時可能不同，這與 a3 自己在
   全三者 deny 組態下觀察到的「相同 config+prompt、不同目錄，2 乾淨/2
   掛起」flakiness 模式相符：**掛起不是 config 的決定性函式，而是某個
   race 的機率性觸發**。
3. **a2 找到的 upstream open issue #35073** 精確符合「已安裝版本
   （1.17.8）」+「headless run 掛起」+「未修復（PR 開著）」，根因是
   sync subagent 的 ask 被誤判為 interactive，等待一個不存在的回應者。
   這個機制完美解釋 a3 觀察到的 flakiness pattern（相同 config 有時掛起有時
   沒有——取決於 agent loop 是否在某次執行中走到 subagent/task 呼叫路徑，
   或某個內部重試觸發了原本該是 deny 但被誤路由成 ask 的分支），比
   a3 自己「哪些 key 被 deny」的框架更能解釋「同 config 不同結果」這件事。
4. a3 發現的 bare-string vs per-pattern-object 差異（`bash:"deny"` 可靠掛起
   vs `bash:{"*":"deny"}` 乾淨）目前最合理的解讀，是 object 形式繞開了
   bare-string 形式會觸發（或更容易觸發）#35073 類 ask-誤判路徑的程式碼分支
   ——而非兩種形式在「deny 語意」上有本質差異（a2 讀到的 `evaluate()`
   對兩者理論上都該解析成 deny）。這是**假設**，非本 spike 直接驗證的結論。

## Recommendation

**(b) 掛起無解但有繞過方式** —— 中等信心（moderate confidence），非高信心；
下方說明競爭假設與需要何種證據才能升級為高信心。

- 最可能的系統性根因是 upstream `anomalyco/opencode` **#35073**（headless
  subagent ask 誤判為 interactive，等待不存在的回應者，PR #35823 未合併）
  ——而非「edit+bash 同時 deny」本身有一個獨立的、schema-specific 的 bug。
  這個假設能解釋 a3 觀察到的 flakiness（同 config 時掛時不掛），比
  a3 標題假設（deny 組合數/特定 key）更貼合證據。
- 但本 spike **未能**直接證明「a3 掛起的那幾次，确实是 #35073 的
  subagent/ask 路徑被觸發」——沒有掛起中途的 process 檢查（a1 的缺口），
  也沒有針對 #35073 修復 PR 打補丁後重跑驗證。因此無法排除還有另一個
  尚未在 tracker 出現、專屬於 bare-string 多重 deny 的獨立 bug。
- **繞過方式（可立即採用於 CC-448 階段 2 manifest）**：
  1. `bash` 一律用 **per-pattern object 形式**（`{"*":"deny"}`）而非 bare
     string `"deny"`，搭配 `edit`/`webfetch` bare deny——a3 樣本雖小（2/2）
     但方向一致，且與「避開觸發 ask-誤判分支」的假設相容。
  2. 無論用哪種 deny 形式，headless dispatch 呼叫 opencode 都必須外掛
     **強制 timeout + kill**（現有 pr-gate/dispatch 逾時機制應已覆蓋，
     CC-470 的逾時止血修復可直接沿用）——把掛起當作已知、有限機率會發生
     的 degrade 情境接受，而非等待 opencode 上游修復。
  3. 升級到 npm 最新 1.17.16 前，需先確認 #35073 是否已在該版本修復
     （PR #35823 截至檢查時仍 open/unmerged，需在實作 CC-438 schema 前
     重新確認一次版本狀態）。

## Open risks

- 未能在掛起當下捕捉 process 狀態（strace/ps/thread dump）；若之後要把
  信心從 moderate 拉到 high，需要在掛起 3–5 秒內能即時介入檢查的 harness
  （例如背景輪詢 `ps --ppid` 而非等到逾時後才檢查）。
- a1 與 a3 對「同一 model、同一 config」得出相反結果（10/10 乾淨 vs 3/3
  掛起）的具體環境差異未定位——不確定是 prompt 措辭、目錄狀態、還是
  model 別名路由到的後端版本差異，需要雙方用完全相同的 harness script
  對跑才能收斂。
- #35073 是否為 a3 掛起的真正根因純屬推論，未經修復-後-重跑驗證；若
  PR #35823 合併後仍可重現 a3 的 bare-string `edit+bash` 掛起，則需要
  重新開一輪 spike 排除掉這個假設。
- bare-string vs object 形式的差異（4 觀察點：row 2/3 vs row 13）樣本數
  過小（3/3 掛起 vs 2/2 乾淨），且 a3 自己在其他組合（全三者 deny、
  edit+doom_loop）發現了 flaky 結果——不能排除 object 形式的「乾淨」
  也只是巧合躲過了同一個機率性 race。
- JS plugin hook 系統（`permission.ask`/`tool.execute.before`）完全未測試
  ——若之後改用 plugin hook 取代宣告式 config 作為繞過方式，需要另一輪
  probe（CC-448 Open risks 已列，本票未縮小範圍）。
