### Accepted, deferred to a follow-up: sequential-mode dispatch not covered (qa-tester-F001, PR #626/#619)

qa-tester flagged that this fix's sandbox-unavailable classification only
covers parallel mode (`pr-gate.sh`'s reviewer classification loop) and not
sequential mode, which retries any non-stale dispatch failure once via
`gate_protocol_single_retry_outcome` regardless of reason.

User-accepted risk, recorded explicitly rather than extending this PR:

- Issue #619's own reproduction is explicitly parallel-mode
  (`tier auto -> full; mode default -> parallel`) — 11/11 Codex sessions
  failed across two gates, ~30 minutes wasted each. This fix closes exactly
  that reported defect.
- Sequential mode's exposure to the same bug is structurally smaller: it
  dispatches one combined session for all reviewers, so a doomed retry
  costs one extra attempt, not a doomed retry multiplied across every
  reviewer. The failure mode this issue was filed over — a ~30-minute,
  11-session waste — does not reproduce in sequential mode's shape.
- Sequential mode's dispatch command streams live to the real stderr
  (`eval "$DISPATCH_CMD" >&2`, no captured log file to grep after the
  fact). Making the signature detectable there means either piping through
  `tee` (changing `$?` capture semantics for dispatch-crash detection, a
  safety-critical path — "an incomplete review cannot certify a valid gate
  result") or capturing silently and re-printing afterward (dropping
  real-time visibility for anyone watching a foreground `pmctl gate run`).
  Both are real trade-offs against a currently-working, safety-critical
  code path, not a drop-in extension of this fix's shape.
- Tracked as a real follow-up (same reason class as this PR, only the
  sequential-mode wiring), not fixed here.

### Disputed and verified incorrect: `_ctx_find_index_files_git` does not double a subtree root's path (critic-F001/qa-tester-F001/architecture-reviewer-F001, PR #625/#620)

critic, qa-tester, and architecture-reviewer independently raised the same
claim: `git -C "$root" ls-files` returns paths relative to the git
**worktree root**, not `$root`, so `_ctx_find_index_files_git`'s
`printf '%s/%s\n' "$root" "$rel"` would double the root's own path segment
when `$root` is a subdirectory of a larger git worktree.

Verified empirically and found factually incorrect, not overridden as an
accepted risk:

- `git -C <dir> ls-files --cached --others --exclude-standard`, run against
  a real repo (git 2.42.0, this host) with a tracked file inside `<dir>`
  and a tracked file outside it, returns only the file inside `<dir>`,
  spelled relative to `<dir>` itself — not the worktree root. This is
  `-C`'s documented contract ("as if git was started in `<dir>`"),
  identical to a plain `cd <dir> && git ls-files`.
- A new permanent regression test, `case_context_index_nested_worktree_subtree`,
  exercises exactly this scenario through the real `pmctl context index` CLI
  path and passes: a subtree index contains only its own eligible files,
  spelled relative to the subtree, with no doubled-root segment and no
  sibling-file leakage.
- The reviewers' claim would be true of `git diff --name-only` / `git status
  --porcelain` (repo-root-relative by default, unless `--relative` is
  given) — `git ls-files` does not share that default. Likely the shared
  origin of this convergent-but-wrong finding across three independent
  sessions.

This is a factual dispute resolved by direct, reproducible evidence, not a
risk tradeoff. Reviewers should not re-raise it against the same code
unless git's actual `-C`/`ls-files` behavior changes.

### Accepted risk: `Edit(/tmp/brief-*)` / `Edit(/tmp/handover-*)` scope (security-reviewer-F001)

security-reviewer flagged that migrating `Write(/tmp/brief-*)` / `Write(/tmp/handover-*)`
to `Edit(...)` grants broad, symlink-able `/tmp` write authority, since a
`Write(<path>)` permission rule never matched anything under this tool's
permission model (only `Edit(<path>)` does).

User-accepted risk, recorded explicitly rather than implemented as a
narrower per-run private directory:

- This scope is not new intent — these exact glob strings were already
  present as (inert) `Write(...)` entries in the user's own settings before
  this change; the fix makes an existing, already-approved permission rule
  actually take effect, it does not expand what was asked for.
- The glob is already the write boundary the executor-dispatch flow enforces
  independently: `runtime/hooks/guard-executor-write.sh` and
  `runtime/lib/handover-validate.sh` both hard-code `/tmp/brief-*.md` /
  `/tmp/handover-*` as the only path shape the dispatch flow will write to,
  so this permission entry is not the sole containment for that path.
- A per-run, ownership- and symlink-safe private directory (the reviewer's
  suggested alternative) is accepted as a real future improvement, not
  something to build as part of this fix. Tracked for later hardening rather
  than blocking this permission-repair change.

### Accepted risk: coarse selected/applied signal, not task-scoped (critic-F001, CC-567)

critic flagged that `memory_applied_scan_brief`'s selected/applied signal is
historical-injection + basename-substring matching, not a task-scoped PM
selection event — a card hit for an unrelated past task counts as
"selected" in every later funnel report, and a coincidental basename
mention in an unrelated brief can register as "applied".

User-accepted risk, recorded explicitly rather than adding an active
task-scoped selection-recording call at the PM/context-pack decision
point:

- This is not a newly-discovered gap — it is the exact tradeoff CC-567's
  pre-impl review named up front (see the ticket's pre-impl artifact,
  "Assumptions / Open Questions": "selected≈injected 的精度犧牲"). The design
  was deliberately chosen over an active-call alternative because this
  repo has direct prior evidence that "record a signal only when an agent
  remembers to call a new command" fails in practice — the previous
  skeleton-episode-field mechanism this same file's `episode_fill_rate_pct`
  measures sat at an 8-12% fill rate for two months before being retired.
  Reintroducing that shape for CC-567 was judged the worse risk.
- The whole point of CC-567 (see its BACKLOG.md "Why this first" section)
  is to gather real applied/outcome evidence *before* deciding whether the
  heavier machinery critic proposes (task-scoped selection events, cohort
  provenance) is worth building. Building it now, inside CC-567, would
  invert that sequencing on the say-so of the same kind of intuition CC-567
  exists to replace with data.
- The coarseness is real and is disclosed in the shipped output: `pmctl
  memory stats` documents this funnel as an approximation, and CC-568
  (gated on CC-567's own data) is the explicit place to revisit whether a
  more precise task-scoped signal is worth its cost, informed by whatever
  this coarse version actually shows.
